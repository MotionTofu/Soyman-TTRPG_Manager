# Как здесь коммитят, пушат и выпускают релиз

Инструкция для любого исполнителя — человека или другой модели, — который
пришёл в этот репозиторий и должен довести правку до пользователя. Порядок
проверен, отклоняться от него не нужно. Всё, что здесь написано, — про этот
конкретный проект, а не про «git вообще».

Отвечать владельцу по-русски.

---

## Что где лежит

| Что | Где |
|---|---|
| Рабочая ветка | `restore/2026-08-24-canvas` — вся работа идёт в ней |
| `main` | подтягивается за рабочей веткой перед релизом, сам по себе не живёт |
| Репозиторий | `github.com/MotionTofu/Soyman-TTRPG_Manager`, **публичный** |
| Сборка релиза | GitHub Actions по тегу `v*.*.*` (`.github/workflows/release.yml`) |
| Версия | `version` в корневом `package.json`, формат `ГГГГ.М.Д` без ведущих нулей |
| Список изменений | `CHANGELOG.md`, по-русски, для читателя-мастера, а не для программиста |
| Задачи | `ToDo.md` (приоритеты и пометка «простая»), `later.md` (отложенное) |

Правила проекта (`CLAUDE.md`) и настройки запуска (`.claude/launch.json`) лежат
в рабочей копии, но **в репозиторий не входят** — они в `.gitignore`. Если вы
видите только клон с GitHub, этого файла и конфигураций у вас нет; всё нужное
из них перенесено сюда.

---

## Красные линии

Нарушение любой из них хуже, чем невыполненная задача.

1. **Не менять рабочую базу владельца.** `server/data/app.db` — живая база, в
   которой он работает прямо сейчас. Читать можно, писать нельзя. Для проверок
   есть копия: `server/data-scratch/app.db` и конфигурации `api-scratch-alt`
   (порт 3002) и `client-scratch` (порт 5174) в `.claude/launch.json`.
2. **Не вводить пароли владельца.** Если приложение просит вход — попросить
   владельца войти самому, а не подбирать и не искать пароль в базе.
3. **Не публиковать «полную» сборку.** `npm run dist:full` собирает сид из
   рабочей базы владельца (`scripts/build-seed.js`) — в ней его личные данные.
   Наружу уходит только «пустая» сборка, её собирает CI.
4. **Не коммитить чужое.** В рабочей копии есть неотслеженные папки владельца
   (например `soysvg/`) — они не часть проекта. Добавлять в коммит только то,
   что относится к сделанной правке; `git add -A` без просмотра `git status` —
   плохая идея.
5. **Перед выкладкой наружу — обзор безопасности.** Повод не выдуманный:
   утечка личных данных в сборочном артефакте один раз уже находилась вручную,
   и только потому, что кто-то посмотрел глазами перед загрузкой.

## Шаг 1. Проверить, что собирается

```bash
npm run build
```

Это `tsc -b` для сервера и `vite build` для клиента. Если падает — чинить, а не
коммитить. Проверка занимает секунды и ловит ровно тот класс поломок, который
иначе обнаружится в CI через пять минут.

Если правка видна в приложении — поднять его и посмотреть глазами: конфигурации
`api` (3001) и `client` (5173) из `.claude/launch.json`, либо scratch-пара для
всего, что трогает данные. «Посмотрите, работает ли» вместо своей проверки —
не ответ.

## Шаг 2. Коммит

```bash
git add <только свои файлы>
git commit
```

Сообщение — по-русски, по образцу соседних коммитов: первая строка называет
сделанное, дальше абзацами **что и почему**, а не перечисление файлов. Отменённые
варианты и причина решения ценнее списка изменений: их потом не восстановить.

В конце сообщения:

```
Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
```

(подставить имя своей модели).

Предупреждения `LF will be replaced by CRLF` — норма для этого репозитория,
игнорировать.

## Шаг 3. Пуш

```bash
git push origin restore/2026-08-24-canvas
```

Если релиза не будет — на этом всё.

## Шаг 4. Релиз

Релиз здесь — это **тег**. Сборку и публикацию делает GitHub Actions; локально
ничего собирать не нужно.

### 4.1. Обзор безопасности

Просмотреть изменения ветки на предмет безопасности (в Claude Code для этого
есть `/security-review`; в другом инструменте — просто прочитать диф глазами,
ища работу с файлами, доступом, чужими данными). Если изменились только тексты
документов или CSS — сказать об этом владельцу прямо, не изображая полный
разбор; если менялся сервер, маршруты, работа с файлами или доступ — разбор
обязателен.

### 4.2. Версия и список изменений

1. В корневом `package.json` поставить сегодняшнюю дату: `2026.8.30` (без
   ведущих нулей — как уже в файле). **Версия не проставляется сама**, а имя
   установщика берётся из неё: забытое обновление даёт релиз, подписанный
   вчерашней датой.
2. В `CHANGELOG.md` заголовок `## Не выпущено` заменить на `## <версия>`; если
   раздела нет — завести с описанием того, что вошло. Пишется для мастера:
   что изменилось на экране и почему, без имён функций.
3. Закоммитить это отдельным коммитом («Версия 2026.8.30 и запись в CHANGELOG»).

### 4.3. Пуш ветки, main и тега

```bash
git push origin restore/2026-08-24-canvas
git push origin restore/2026-08-24-canvas:main
git fetch origin && git branch -f main origin/main
git tag -a v2026.8.30 -m "SoyMan_ttrpg 2026.8.30" <хеш коммита с версией>
git push origin v2026.8.30
```

`main` подтягивается fast-forward: своей истории у него нет, слияние не нужно.

### 4.4. Дождаться сборки

```bash
gh run list --workflow=release.yml --limit 1
gh run watch <id> --exit-status
```

Идёт около пяти минут. Собирается на `windows-latest`, Node 22.

### 4.5. Опубликовать черновик — обязательный шаг

Воркфлоу выкладывает релиз **черновиком**, а черновик `electron-updater` не
видит: пока он не опубликован, обновление до пользователей не доходит.

```bash
gh release edit v2026.8.30 --draft=false --latest \
  --title "SoyMan_ttrpg 2026.8.30" --notes-file <файл с описанием>
```

Описание — короткая выжимка из `CHANGELOG.md`, тем же языком.

### 4.6. Проверить, что обновление поедет

```bash
curl -sL https://github.com/MotionTofu/Soyman-TTRPG_Manager/releases/latest/download/latest.yml | head -3
```

Должна вернуться свежая версия и имя установщика. В самом релизе должны лежать
четыре файла: `latest.yml`, portable-`.exe`, установщик `-Setup-.exe` и его
`.blockmap`.

## Локальная сборка (нужна редко)

Только если релиз собирается не через CI — например для «полной» сборки, для
себя, без публикации.

1. **Остановить dev-серверы** (`api`, `client`), если они подняты.
   `electron-rebuild` пересобирает `better_sqlite3.node`, а запущенный сервер
   держит файл открытым — сборка падает с `EPERM: operation not permitted`.
2. Проставить версию в `package.json` (см. 4.2).
3. `npm run dist:empty` — пустая сборка; `npm run dist:full` — с сидом из базы
   владельца, **наружу не выкладывается** (красная линия №3).

## Частые грабли

- **Релиз выпущен, а обновление не приходит.** Забыт шаг 4.5: релиз остался
  черновиком.
- **CI падает на `better-sqlite3`.** Нужен Node 22: под Node 20 готовых
  бинарников больше нет, а сборка из исходников на раннере не проходит. В
  воркфлоу это уже прописано — не понижать.
- **`npm run dist` падает с `EPERM`.** Не остановлены dev-серверы.
- **Имя установщика со вчерашней датой.** Не проставлена версия перед сборкой.
- **Правка «не видна» в запущенном приложении.** Клиент держит свою копию
  данных на окно; после правок данных страницу надо перезагрузить. А если
  что-то менялось в серверном коде — перезапустить `api`.
