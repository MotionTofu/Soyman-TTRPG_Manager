# Архитектура: расчёты, селфхост, коммерция — план и рекомендации (2026-09-06)

Итог разбора от 2026-09-06. Живые базы почти пустые — окно для ломающих изменений открыто. Цель документа: зафиксировать решения, чтобы потом не было боли.

## 1. Где расчёты сейчас

- **Клиент** — весь D&D-движок: `abilityModifier / computeProficiencyBonus` (`AbilityScores.tsx`), `computeArmorClass` (`armorClass.ts`), `spellSlotsAtLevel / computeSpellSlots / effectiveCasterLevel` (`progression.ts`, `dndSlots.ts`), АТК/СЛ/навыки/истощение (`DndCharacterForm.tsx`), пулы ресурсов (`dndResources.ts`).
- **Сервер** — агрегаты и хранение: `campaignEarnings / sessionEarnings / totalEarnings / unpaidSessionsForPlayer / debtsForCampaign` (`services/finance.ts`), `content` статблоков как непрозрачный JSON + `mergeContentPatch` + `broadcastCharacterUpdate` (`routes/statblocks.ts`).
- **Дубль с расхождением:** `defaultStake()` (`SessionDetailPage.tsx`) умеет `per_table` + `per_month`, серверный `unpaidSessionsForPlayer()` — только `stake_override` + `per_table`, `expectedPerPlayer()` (`SessionOutcomeModal.tsx`) — третий клон. На месячном тарифе три места покажут три «долга».

## 2. Решение по расчётам: общий пакет, не переезд

**Не переносить «всё» на сервер.** Чистая математика листа (`f(лист)`, микросекунды на кейстрок) умрёт от RTT даже на localhost. Деньги — наоборот, должны стать сервер-авторитетными (спор людей, а не циферки).

- `packages/rules/` — ноль зависимостей от React/Express. Туда: `armorClass.ts`, `progression.ts`, `dndSlots.ts`, чистая часть `AbilityScores`, `expectedStake`. Клиент считает optimistic preview синхронно, сервер — то же самое при валидации/чтении. Один код — ноль расхождений.
- Клиентские `defaultStake / expectedPerPlayer` — урезать до тонкой обёртки над общим `expectedStake`.
- Серверу добавить батч `POST /systems/entries/meta` (убрать N+1 `fetchEquipmentMeta` по запросу на предмет) и `GET /statblocks/:id/computed` для сверки preview vs сервер.
- Жёсткость сервера: zod-схемы `attendance` + `statblock content`, `CHECK(amount_paid >= 0)`, `baseUpdatedAt` для `attendance` (для статблоков 409 уже есть), `debtsForCampaign` переписать одним `GROUP BY` вместо цикла с `COUNT(*) per session`.
- Хранить source, а не derived: `proficiencyBonus: "+2"` строкой и `armorClass` строкой рядом с вычисленным — источник рассинхрона. Вычисляемое не хранить.

## 3. Решение по жизни приложения: домашний сервер — источник истины

От «одинаково важных» отказаться как от цели: равноправный multi-master = oplog + резолв конфликтов + синк бинарников волта, месяцы работы и вечные split-brain с живыми кампаниями внутри.

- **Целевая модель:** селфхост 24/7 — единственный источник истины. Electron — лучший клиент к нему (remote-mode: настраиваемый URL сервера) + встроенный сервер как fallback для стола без сети + кнопка «залить локальное на домашний».
- **Пока данных мало — сделать фундамент (ломающие изменения, потом будет поздно):**
  1. `uid TEXT UNIQUE` на все синкабельные сущности (сейчас `id AUTOINCREMENT` везде, `uid` лишь частично). Внешний мир — только по `uid`.
  2. `updated_at` всем таблицам + append-only `sync_log(seq, table, uid, op, device_id, ts)`.
  3. Нормализация хранимых путей (`\` → `/` на чтении/миграции) — иначе Windows-БД не встанет на Linux.
  4. Один способ запуска: Docker-образ + compose (volumes `data/vault/config/backups`), Caddy с авто-HTTPS, Tailscale как рекомендованный доступ извне.
- **Не делать сейчас:** общий auto-sync/CRDT (хватит ручного `backup zip → restore` + разового push), уход с SQLite (один writer — её идеальный кейс), вторая БД для игроков (доступ уже правильно режется `apiRoleGate + playerRouter`).

## 4. Linux-деплой: вердикт

Технически — да, сервер на ~95% переносим (всё через env, `xdg-open`-ветка есть, пребилды `better-sqlite3/sharp` под Linux существуют, `db.backup()` в WAL работает). Единственная блокер-правка — п.3 выше про пути. `deploy/` причёсан 2026-09-06 (см. раздел 7).

## 5. Доступ через интернет «как Foundry»: вердикт

Локалка — штатно (`isPrivateHost`, основной сценарий). Интернет с дома — руками, one-click как у Foundry нет (нет UPnP/DDNS/пригласительных ссылок). Копировать Foundry (проброс порта) — худший вариант: CGNAT, серый IP, сон Windows, светить комп наружу.

- Рекомендация: LAN из коробки → удалёнка через Tailscale/ZeroTier (без открытых портов, за CGNAT работает) → опционально Cloudflare Tunnel → опционально дешёвый VPS 24/7. Код под всё это уже готов, HTTPS обязателен снаружи.

## 6. Свой Forge: вердикт

Сможем как оркестратор однотенантных инстансов (один клиент = один контейнер: своя SQLite + волт + `JWT_SECRET`), не переписывая движок под мультитенант. Лестница: Forge-lite (Docker-образ + «разверни за 5 минут», без чужих данных у нас) → managed single-tenant за подписку → true multi-tenant не делать. Это смена продукта (саппорт, биллинг, чужие данные), не фича.
