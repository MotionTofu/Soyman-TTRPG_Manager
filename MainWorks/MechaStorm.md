## 1. Что реализовано (факты, без оценок)

### 1.1. Вычисляемые механики D&D 5.5 — персонаж

Хранится в JSON статблока `dnd_character`, считается на клиенте:

- Модификатор характеристики: `floor((score-10)/2)` (`AbilityScores.tsx:124-126`).
- Бонус мастерства: `2+floor((total-1)/4)`, мин. уровень 1, кап 6 (`AbilityScores.tsx:105-109`). Суммарный уровень — сумма по классам (`:98-100`).
- Каст-атрибут — от первого класса с `spellcastingAbility` (`:114-122`).
- Сейвы/навыки: `mod + prof*level − penalty`, экспертиза `level=2`, сейвы `0/1` (`AbilitySavesSkills.tsx:22-30`). Штраф истощения идёт в сейвы/навыки, не в КД/СЛ (`:24-27`).
- КЗ (`armorClass.ts:28-77`): без брони `10+Лов`; с бронёй — макс. КЗ из надетых (не щит) + `magicBonus`; тяжёлая игнорирует Лов; средняя `min(dex,cap)`, `cap=0 → 0`; щит — лучший из надетых; плюс сумма `acBonus` и `manualBonus`; только `equipped && !transferOut`.
- Ячейки (`dndSlots.ts`): `casterKind` по 20-му уровню (full ≥ 6 круг, half = 5, third > 0); эффективный уровень кастера (full целиком, half/2, third/3 вниз, пакт исключён); 1 кастер — своя строка, >1 — таблица полного по эфф. уровню; пакт отдельно. Данные берутся из `data.progression` класса, не зашиты (`progression.ts:175-212`).
- Ресурсы/пулы (`dndResources.ts`): максимум НЕ хранится, вычисляется из колонок `resource/stat` таблицы развития; хранятся только «израсходовано + внешняя прибавка»; ключ `prog:classId:colKey`; формульные исключения (Возложение рук `ур*5`, Вдохновение `max(1,мод.Хар)`, Избранный враг = БМ); `recharge: long|short|none`.
- Атака заклинаний / СЛ / пассивное восприятие (`DndCharacterForm.tsx:6576-6608`): атака = мод.каста + БМ + misc − истощение×2; СЛ = 8 + мод + БМ + misc (без истощения); пассив = 10 + Мдр + БМ×владение − истощение×2; урон скорости от истощения ×5 футов.
- Кости хитов: `computeHitDice` из `classHitDieCache` (`ур.кN` join `+`); возврат на длинном `max(1,floor(total/2))` сначала где потрачено больше.
- Отдых: короткий — только `pactSlotsUsed=0 + resetResources("short")`, кости вручную; длинный — ячейки/пакт/ресурсы(long)/ХП/temp/сейвы от смерти/концентрация сброс, истощение −1; `recharge=none` не трогается.
- Концентрация: хранится строкой; чек `СЛ max(10,floor(урон/2))`.
- Снаряжение: `fetchEquipmentMeta` кэширует `armorType/ac/max_dex_bonus/ac_bonus/damage/attack_/weapon_properties/mastery`; стартовые наборы из `equipment_a|b_items|manual|gold`.
- Заклинания персонажа: `spellsByLevel/cantrips + spellSlotPips/Used`, `prepared 0|1|2`; сортировка «подготовленные наверх»; гранты вида/подкласса через `recomputeGrantedSpells`.
- Спутники: `DndCompanion[] {entryId, name}` — ссылка с именем рядом с id (правило репозитория).
- Действия: `weaponAttackRows + combatSpellRows + featureActionRows + manualAttackRows`.

### 1.2. Существо D&D 5.5

Хранится (`DndCreatureForm.tsx:119-156`): `size, creatureType, alignment, armorClass{value,note}, hitPoints{diceCount,dieSize,bonus,formula}, speed{walk,fly,swim,climb,burrow,hover,note}, initiativeBonus, challenge{rating,proficiencyBonus}, abilities, savingThrowProfs, skillProfs, damageVuln/Res/Imm, conditionImm, senses, languages, spellcasting, traits/actions/bonus/reactions/legendary/lair, habitat/treasure/equipment/loot`.

Вычисляется:

- БМ от КО: ≤4:+2, ≤8:+3, ≤12:+4, ≤16:+5, ≤20:+6, ≤24:+7, ≤28:+8, иначе +9.
- Атака/СЛ: `мод.хар + БМ`, `СЛ = 8 + мод + БМ` (`dcOverride` в приоритете); для действий `DC = 8 + БМ + мод`.
- Хиты: `среднее = floor(N*(K/2+0.5)) + бонус`, формат `среднее (кости)`; бросок в инициативе через `diceRoll.ts`.
- Скорость: хранение всегда в футах, формат из футов; легаси-парсинг строк.
- КД/скорости/макс. бонус атаки и СЛ для карточки считает клиент теми же функциями, что рисуют полный статблок (`creatureCard.ts:12-15`). Выбор статблока: первый `dnd_creature`, `full` перед `brief`; наследование от `base_monster_id` на лету без копирования; портрет свой иначе шаблонный.
- Серверная двусторонняя синхронизация сводки монстра `size/creatureType/alignment/challenge ↔ статблок` (`monsterSummary.ts`, `systems.ts:412-491`).

### 1.5. Сортировки — что есть сейчас

- Бестиарий (`MonsterSection`): `alpha | creature_type | cr | size`. `cr/size` только при `systemCode==='phb'`. Повторный клик инвертирует направление. Персист `localStorage compendium-sort-*`. Классы в пикерах — по алфавиту, не по `position`.
- Справочник (`CompendiumSection`): `manual | alpha | level | school | type | rarity`, дефолт `spell:level, mechanics:alpha, else:manual`. Реально сортирует только `alpha` (`name.localeCompare(ru)` + `reverse()`); `level` — группировкой. В дереве — `childrenOf(parentId) sort position`.
- Транспорт (`VehicleSection`): сортировки вида `alpha | category | size` на уровне грида; фильтры отдельно.
- Ресурсы (`ResourcesListPage`): `az | size | date` (`name ru / size_bytes desc / created_at desc`).
- Архив (`ArchivePage`): `date | name | type` + направление.
- Карты (`MapsListPage`): `recent (updated_at desc) | az (name ru)`.
- Кампании/настройки/игроки: сортировки нет (поиск + группировка вкладками групп).
- Календарь/хроника: `WorldSort asc|desc`, `chronicleSort asc|desc by date`, `chronicleSort: chronological|important-first` в сеттинге; сессии `sort date asc`; журнал персонажа `filter !cancelled sort date desc`.
- `StatblockList`: сортировки нет — прямой список `statblocks[] + archived[] + templates[]`.
- Звук/плейлисты: сортировки нет (группировка по ролям `background/ambient/weather/stinger`).
- Здоровье (`HealthPage`): сортировки нет — только счётчики и фильтры.

## 2. Пространство альтернатив (педантично, без примеров)

Для каждой реализованной вещи — оси, по которым решение могло быть другим. Без суждений «лучше/хуже», только перечисление степеней свободы.

### 2.1. Вычисление vs хранение

1. Источник формулы: захардкожена в коде / читается из данных прогрессии класса / задаётся выражением в записи справочника / вычисляется сервером / дублируется на обеих сторонах.
2. Момент вычисления: при отрисовке / при сохранении (снапшот) / при изменении зависимости (реактивно) / по кнопке «пересчитать» / фоном по расписанию.
3. Перекрытие: ручной ввод всегда побеждает формулу / формула всегда побеждает / ручной бонус отдельным слагаемым (`misc`, `manualBonus`, `acBonus`) / ручное значение только при пустой формуле / запрет ручного ввода вовсе.
4. Гранулярность перекрытия: целиком (своё КЗ вместо всего расчёта) / послагаемым (свой мод, свой БМ, своя кость) / один флаг «посчитано вручную».
5. Округление и направление: `floor` / `ceil` / `round` / `trunc`; где режется (на каждом шаге vs в конце); отрицательные значения (пол vs потолок vs ноль).
6. Капы и полы: есть / нет; жёсткие (не пробиваются бонусами) / мягкие (пробиваются `misc`); видимость капа в UI (показывать «срезано капом» или молча).
7. Порядок применения: база → бонусы → умножения → капы; или бонусы до капа / после капа; щит до `magicBonus` / после.
8. Истощение/состояния как модификаторы: вычитаются из итога / из слагаемого / отключают слагаемое целиком / меняют формулу (другая ветка); складываются аддитивно / мультипликативно / берётся худшее.
9. Пулы: максимум вычисляется / хранится / гибрид (вычислено + внешняя прибавка); потраченное хранится счётчиком вверх / остаток счётчиком вниз; восстановление по кнопке / автоматически по отдыху / вручную по единице.
10. Ячейки мультикласса: сумма по таблице полного / каждая строка отдельно / гибрид (своя + общая); пакт внутри общей / всегда отдельно / опционально.
11. Наследование (существо от `base_monster_id`): на лету без копирования / копированием при создании / ссылкой с точечными перекрытиями / заморозкой версии.
12. Синхронизация сводки ↔ статблок: двусторонняя живая / односторонняя (сводка → статблок или наоборот) / по кнопке / только при сохранении / нет вовсе (два независимых поля).
13. Сервер считает vs клиент считает: сервер — источник правды, клиент рисует / клиент считает, сервер хранит сырьё / оба считают независимо / считает тот, кто показывает (карточка vs лист разными функциями vs одной).

### 2.2. Сортировка

1. Ключей: один / несколько (первичный + вторичный + третичный); фиксированная цепочка (инициатива → dex → имя → id) vs настраиваемая.
2. Направление: `asc | desc` глобально / на каждый ключ своё / инверсия повторным кликом / трёхстадийный цикл (`asc → desc → нет`) / без инверсии вовсе.
3. Пустые/незаданные: всегда в хвосте / всегда в голове / по направлению (в хвосте при `asc`, в голове при `desc`) / отдельным блоком «Не указан» / скрыты вовсе.
4. Тип сравнения: лексикографическое (`localeCompare`) / числовое / естественное (`10` после `9`, а не после `1`) / по кастомному порядку (`CR_ORDER`, `CREATURE_SIZES`) / по дате (создания / изменения / игровая внутри мира / реальная).
5. Локаль и регистр: с учётом русской локали / без; регистронезависимо / сначала заглавные; диакритика и `ё/е`; префиксы-артикли и скобки (`[Fighter]`, `(Ифрит)`) — режутся / учитываются / выносятся в отдельное поле.
6. Стабильность: стабильная (равные сохраняют входной порядок) / нестабильная; входной порядок — `position` / `id` / `created_at` / случайный.
7. Ручной порядок: `manual` как сортировка (`position` drag-drop) / ручной порядок как перекрытие поверх сортировки (закреплённые наверх) / ручного нет вовсе.
8. Избранное: отдельный блок сверху / обычная строка со значком / закрепление внутри своей группы / отдельный фильтр вместо сортировки.
9. Область: сортируется весь список / внутри каждой группы отдельно / группы между собой отдельно от строк внутри / избранное сортируется иначе, чем остальное.
10. Персистентность: запоминается на пользователя+секцию / глобально / не запоминается; миграция legacy-ключа / сброс при смене системы; дефолт разный на вид контента (`spell:level, mechanics:alpha`).
11. Видимость управления: переключатель всегда виден / скрыт за меню / отсутствует (один зашитый порядок, как сейчас в кампаниях и `StatblockList`).

### 2.3. Фильтрация

1. Логика композиции: AND всех активных / OR внутри одного фасета + AND между фасетами / произвольная формула / только один активный фильтр за раз.
2. Исключение: только включение (`показать X`) / включение + исключение (`показать X, спрятать Y`) / инверсия всего набора («кроме»).
3. Пустые значения: попадают под любой фильтр / только под «Не указан» / скрываются при любом активном фильтре / отдельный чекбокс «показывать пустые».
4. Каскады: независимые списки / зависимые (подкласс только внутри выбранного класса; опция с нулевым выхлопом disabled vs скрыта vs показана с `0`).
5. Источник опций: из данных (что есть в списке) / из справочника механик (все возможные, включая нулевые) / гибрид (все + счётчики).
6. Счётчики: есть (`filtered/total`, `N из M`) / нет; считаются до применения своего фасета (сколько даст опция) vs после всех.
7. Сброс: одна кнопка «сбросить фильтры» (сортировку не трогает, как сейчас) / сброс всего включая сортировку и поиск / сброс пофасетно / без кнопки (крестики на каждом чипе).
8. Представление активных: чипы с крестиками / строка «активно: X» / молча (видно только по результату) / URL-параметры (делимая ссылка).
9. Пресеты: нет / именованные наборы («готовые фильтры») / временные vs сохранённые / общие для всех vs личные.
10. Время жизни: сбрасываются при уходе со страницы / живут в `localStorage` / живут в URL / живут до ручного сброса.
11. Фильтр как доступ: `favOnly`, `showCancelled`, `player_visible`, `visible|hidden` — это фильтр отображения / фильтр прав / отдельный режим, а не фильтр.

### 2.4. Поиск

1. Область: по имени / по имени+описанию / по всем полям (`searchableText`) / по выбранным типам (`types=compendium_entry`) / по связям (тексты кампании vs тексты системы).
2. Триггер: с первого символа / со второго (как сейчас в палитре) / по Enter / по кнопке / живой с debounce (200мс) / живой без debounce.
3. Совпадение: подстрока (`includes`) / префикс / целые слова / регулярка / нечёткий (опечатки, расстояние) / стемминг (падежи) / транслитерация (латиница ↔ кириллица) / синонимы (`aliases`, `name_original`).
4. Регистр и нормализация: как есть / нижний регистр / `ё→е` / скобки и пунктуация режутся / цифры словами и наоборот.
5. Ранжирование: порядок списка сохраняется / точные сверху (`exact|likely|doubtful`, как в визарде) / вес по полю (имя > описание > связи) / без ранжирования (плоский `slice 40 / slice 8`).
6. Ограничение выдачи: `slice N` без «показать ещё» / пагинация / «показать все N» / виртуализация; что режется первым (глубокие уровни дерева vs дальние группы).
7. Пустой запрос: показывает всё / показывает ничего / показывает «рекомендованное» (выкладка до поиска) / показывает последнее.
8. Подсветка: есть (что совпало) / нет; авто-expand веток / только совпавшие строки без предков / предки серым.
9. Сервер vs клиент: ищет клиент по загруженному / сервер по `q=` / гибрид (первые N клиентом, остальное сервером).
10. История: нет / последние запросы / сохранённые запросы / общие для группы.

### 2.5. Группировка

1. Основание: по полю (тип, школа, уровень, размер, КО) / по первой букве / по диапазону (уровни 1–4, 5–10) / по тегу (перекрывающиеся группы, строка в двух группах сразу) / без группировки (плоский список).
2. Вложенность: один уровень / дерево (`childrenOf(parentId)`) / смешанная (группы + дерево внутри); предки при поиске остаются / скрываются.
3. Порядок групп: тот же `dir`, что у строк / свой (группы A→Я, строки внутри Я→А) / кастомный (`CR_ORDER`) / по размеру группы / вручную.
4. Заголовки: с названием + счётчиком / только название / sticky-заголовки при прокрутке / без заголовков (разделители).
5. Свернутость: всё развёрнуто / всё свёрнуто / запоминается (`bestiary-group-*`) / `forceOpen` при поиске / кнопка «развернуть/свернуть всё».
6. Незаданное: группа «Не указан» в хвосте / в голове / нет группы (строки без значения скрываются при группировке) / значение подставляется по умолчанию.
7. Избранное как группа: отдельный блок сверху + исключение из основных групп (как сейчас) / дублирование (и в избранном, и в своей группе) / не группа, а бейдж.
8. Группировка vs фильтр: группировка переключает раскладку, фильтр режет строки (как сейчас) / группировка = фильтр «показать только эту группу» / одно и то же управление на оба.

## 3. Аналоги из других областей (примеры — на мне)

Принцип: для каждой оси из раздела 2 — где такое уже решали и как. Без рекомендаций «брать это», только карта вариантов. Помета `→ стол` — где аналог особенно ложится на критерий «простота для Мастера» (руки заняты, взгляд урывками, настройка в момент вождения проигрывает).

### 3.1. Сортировка: кто как выкручивался

1. **Таблицы (Excel / Google Sheets / Airtable).** Мультиключ: сортировка по нескольким столбцам с порядком приоритетов + трёхстадийный цикл `asc → desc → нет`. Пустые всегда вниз отдельным флагом. `→ стол`: цикл из трёх состояний удобен там, где сортировку трогают редко; за столом лучше двухстадийный (как сейчас), чтобы не кликать лишний раз.
2. **Файловые менеджеры (Total Commander / FAR / Finder).** Отдельные правила для папок vs файлов (папки всегда сверху независимо от направления) — прямой аналог «Избранное всегда сверху» и «Не указан всегда в хвосте». Сортировка папок и файлов разными ключами одновременно.
3. **Интернет-магазины (Ozon / Wildberries / Steam-стор).** Один видимый селект `Популярные / Дешевле / Дороже / По рейтингу / По скидке` вместо матрицы ключи × направления. Направления зашиты в опцию. `→ стол`: за столом «КО ↑ / КО ↓» как две опции в списке проще, чем ключ + стрелка.
4. **Почта (Gmail / Outlook).** Сортировок почти нет — есть один порядок (новые сверху) + фильтры-ярлыки + поиск. Спорный полюс: вообще убрать сортировку там, где её заменяют группировка и поиск (как сейчас в кампаниях — и это работает).
5. **Плееры (foobar2000 / iTunes).** Сортировка плейлиста vs сортировка библиотеки — разные дефолты и разная персистентность. Аналог идеи «сортировка бестиария ≠ сортировка пикера заклинаний», хотя сейчас у них общий механизм.
6. **Трекеры (Jira / YouTrack).** JQL и сохранённые фильтры как именованная сортировка+фильтр в одном (`ORDER BY priority DESC, created ASC`). Полюс «сортировка как текстовая формула», а не кнопки.
7. **Игры (коллекции Hearthstone / MtG Arena).** Сортировка по мане/стоимости с группировкой по ней же одновременно — то, чего сейчас нет: в справочнике `level` сортирует группировкой, а не строками. У них это один жест.
8. **Естественный порядок (файловые менеджеры, `ls -v`).** `10` после `9`, а не после `1`. Сейчас в проекте сравнение строковое (`localeCompare`), для имён вида «Гоблин 10» даст неверный порядок.

### 3.2. Фильтры: фасеты придуманы до нас

1. **Сторы (Steam / Ozon / DNS).** Фасеты с счётчиками: у каждой опции в скобках сколько даст (`Эльфы (12)`), опции с нулём — disabled, но видны. Каскад: выбрал жанр — схлопнулись платформы. У нас счётчики есть только `filtered/total`, а «сколько даст опция до клика» — нет.
2. **Gmail-чипсы.** Активные фильтры — снимаемые чипсы + кнопка «сбросить всё». У нас сброса фильтров без сброса сортировки нет как чипа — только кнопка. Чипсы решают проблему «что сейчас включено и почему список короткий».
3. **Notion / Airtable Views.** Фильтр+сортировка+вид сохраняются как именованный View («Бестиарий для боя», «Заклинания волшебника 3»). Это следующий уровень после пресетов: не «сохранённый фильтр», а «сохранённый экран целиком».
4. **Lightroom / Darktable.** Фильтры по метаданным (рейтинг, флаг, цвет) + текстовый фильтр одновременно; инверсия («все, кроме отбракованных») одной галочкой. Аналог недостающей у нас инверсии и `favOnly` как флага, а не фильтра.
5. **Авиаагрегаторы (Aviasales).** Ползунки-диапазоны (цена, время, пересадки) + чекбоксы. Прямой аналог фильтра по КО как диапазону («КО 0–2»), а не точечным выбором.
6. **IDE (VS Code Problems / Git log).** Фильтр как строка запроса с операторами (`is:open author:me`), а не форма. Полюс для визарда связей: `exact|likely|doubtful` можно выразить строкой, а не тирами-блокам��.
7. **Splitwise-подход к «пустым».** Отдельный тумблер «показывать без категории» вместо группы «Не указан». Группа в хвосте (как у нас) прячет проблему неполных данных; тумблер делает её явной.

### 3.3. Поиск: от `includes` до нечёткого

1. **Лаунчеры (VS Code Ctrl+P / Raycast / Everything).** Нечёткий матч по подпоследовательности (`гбл` → «Гоблин»), ранжирование по плотности совпадения, последние выбранные — выше. Наш `includes` требует точной подстроки и проигрывает на падежах («гоблина» не найдёт «гоблин»).
2. **Поиск с морфологией (Яндекс / Elasticsearch с русским стеммером).** Падежи, `ё/е`, транслит (`goblin` → «гоблин») нормализуются до сравнения. У нас нормализации нет — ближайший дешёвый шаг без полного нечёткого поиска.
3. **Obsidian / grep.** Поиск по содержимому + бэклинки: строка находится не только по имени, но и по упоминаниям в других текстах. Наш поиск по `searchableText` — зачаток этого; полный вариант — искать заклинание по классу, который его даёт, а не только по его own записи.
4. **Маркетплейсы: «выкладка до поиска».** Пустой запрос показывает «рекомендованное», а не всё (уже принято для пикеров заклинаний в чарнике — раздел 2 чарник-спеки). Распространяется и на бестиарий: пустой бестиарий → «часто используемые в этой кампании».
5. **Подсветка (браузер Ctrl+F / IDE).** Совпавшая подстрока подсвечена, `Enter` прыгает по совпадениям, предков раскрывает автоматически. У нас авто-expand есть, подсветки нет — за столом подсветка важнее, чем кажется: Мастер ищет глазами, а не читает.
6. **Ограничение выдачи (Google `показано 10 из N` / Discord `slice 50`).** Честное «нашлось 300, показаны 40» + кнопка «показать всё». У нас `slice 40 / slice 8` молча режет — Мастер не знает, что список обрезан.

### 3.4. Группировка: таблицы сводных и канбан

1. **Сводные таблицы (Excel Pivot).** Группировка по двум осям сразу (строки — тип, колонки — КО) + агрегат в ячейке (count, avg). Наш максимум — одна ось. Две оси для бестиария («тип × КО») — классический запрос «кого бросить против партии 3 уровня».
2. **Канбан (Trello / Jira-доска).** Группа = колонка, карточка таскается между группами (смена значения поля drag-drop). Аналог: перетащить существо из группы «КО 1» в «КО 2» = поменять КО. Сейчас группы только читают поле.
3. **Почтовые треды (Gmail).** Сворачивание по треду с показом «3 из 5 прочитано». Аналог для групп справочника: «Уровень 3 (2/5 подготовлено)».
4. **Проводник Windows «Группировать по».** Любая колонка становится группировкой одним кликом из контекстного меню заголовка. У нас группировка = сортировка (один селект на оба). Разделение «сортировать по X, группировать по Y» — оттуда.
5. **Перекрывающиеся группы (теги в Bear / Todoist-метки).** Строка живёт в двух группах сразу. Сейчас строка в одной группе (или в «Избранном» вместо своей). Для снаряжения (оружие + магическое) перекрытие естественнее.

### 3.5. Виды и плотность: один контент — пять тел

1. **Notion / ClickUp / Airtable.** Один набор данных — виды Table / Board / Calendar / Timeline / Gallery, переключаемые табом, настройки каждого запоминаются отдельно. Наш `grid|list` — минимальный вариант этого; календарь кампании (`calendar|list|axis`) — второй росток того же.
2. **Табличный вид с сортируемыми колонками (Airtable / Jira-таблица).** Клик по заголовку сортирует, повторный инвертирует, `Shift+клик` добавляет ключ. Заменяет отдельный селект сортировки.
3. **Плотность (Gmail Comfortable/Cozy/Compact / VS Code `editor.lineHeight`).** Три плотности вместо одного размера плитки. `→ стол`: на телефоне за столом компакт, на десктопе при подготовке — комфорт.
4. **Пагинация vs бесконечность (ВК-лента vs GitHub Issues).** У нас в архиве `visible 50 slice` — гибрид «кнопка + счёт». Чистые полюса: постранично с номерами (делимая ссылка «страница 3») vs виртуализация на тысячах строк (сейчас тысячи записей компендиума рендерятся группами без виртуализации — потенциальный затык).
5. **Колода как вид (Tinder-стопка / Anki).** Наш чарник-колода (свайп + веер) — оттуда же. Обратный перенос: веер миниатюр как вид для узлов холста («все сцены веером») вместо поиска по узлам.

### 3.6. Вычисления: формулы, слои и перекрытия

1. **Таблицы (Excel `=A1+B1`, Google Sheets `ARRAYFORMULA`).** Формула — текст в ячейке, видна и правится на месте, пересчёт реактивный, перекрытие — просто вписать число поверх формулы (с потерей формулы). Наш полюс «формула в коде + `misc` сбоку» — противоположный: формула не видна, но и не ломается случайным вводом. `→ стол`: Мастеру за столом вписать число поверх быстрее, чем искать поле `misc`.
2. **D&D Beyond.** Считает всё, перекрытия — тумблерами («своё КЗ»), каждое перекрытие подписано «overridden». У нас перекрытия без подписи «вручную» — не видно, где правда, где формула.
3. **Foundry VTT (система dnd5e).** Формулы-бонусы как строки `@abilities.dex.mod + @attributes.prof` в полях предметов и эффектов; активные эффекты меняют итог без правки базы. Наш `DndCost.resourceKey` + эффекты — зачаток того же; полный вариант — эффекты предметов правят КЗ/атаку живой формулой.
4. **Видеоигры (Path of Exile / Diablo).** Слои модификаторов: база → increased (сумма %) → more (произведение) → кап. Порядок слоёв — часть правил, показывается в тултипе разложением. Наш расчёт КЗ — плоская сумма; слои понадобились бы при сопротивляемостях/уязвимостях в уроне (сейчас `damageVuln/Res/Imm` только хранятся, урон ими не правится).
5. **Бухгалтерия (1С / ERP).** Документ vs регистр: первичка хранится, итоги — движением, пересчёт — перепровеAIдением. Наш аналог: статблок — документ, сводка монстра — регистр; сейчас синхронизация живая двусторонняя, а могла быть «перепровести» по кнопке (предсказуемее при импортах).
6. **Кэширование итогов (Notion Rollup / Airtable).** Итог считается фоном и хранится (снапшот), правится только пересчётом. Полюс против нашего «считать при отрисовке»: быстрее на тысячах строк (бестиарий), но врёт между пересчётами.
7. **Наследование (ООП / CSS-каскад / Figma-стили).** `base_monster_id` на лету (как у нас) = наследование без копирования; копирование при создании = отвязка; перекрытия точечно = каскад. CSS-аналог честно показывает, откуда каждое значение (инспектор «перечёркнуто наследованное») — у нас источник перекрытия не виден.

### 3.7. Инициатива: пять школ порядка ходов

1. **Классика D&D (как у нас).** Бросок + dex, фиксированный порядок, раунды. Альтернативы ниже — замены именно этого ядра.
2. **Side / Popcorn (Fate, Savage Worlds без карт).** Ходит сторона, внутри стороны — кто готов; popcorn — текущий выбирает следующего. Убирает трекер как список чисел, остаётся «чья сторона». `→ стол`: меньше учёта, больше живости; цена — Мастер держит в голове, кто уже ходил (фишки/галочки).
3. **Карты (Savage Worlds).** Каждому тянут карту, порядок — достоинство+масть, джокер — бонус. Ничьих нет по построению, тасование — ритуал. Аналог цифрового «перетасовать порядок» вместо «перебросить всем».
4. **Слоты (Genesys / FFG Star Wars).** Число слотов = числу участников, слоты делятся на геройские/злодейские, кто в какой слот — решают внутри стороны каждый раунд. Компромисс между классикой и popcorn.
5. **Часы и тики (Blades in the Dark, Apocalypse World).** Нет порядка — есть часы угроз и ходы по триггерам («логово на 20» у нас — уже зачаток часов, записанный числом). Полный вариант: вместо трекера — часы босса + ходы игроков по готовности.
6. **Тактическая лента (Divinity Original Sin / Baldur's Gate 3).** Портреты лентой сверху, текущий крупно, следующих видно на 2–3 вперёд, отложенный ход — увод портрета вбок. Наш трекер — список строк; лента — тот же порядок, но показ «кто на подходе» важнее, чем полный список.
7. **Тик-система (Hackmaster / Feng Shui).** Каждый приём стоит N тиков, инициатива — счётчик времени, а не раунды. Полюс для задумчивых: точный, но требует учёта за столом — против «простоты для Мастера».

### 3.8. Ресурсы и отдых: мана придумана трижды

1. **Заряды vs мана (MtG-слоты vs Diablo-мана).** У нас слоты-заряды (как MtG). Полюс маны: общий пул очков, заклинание стоит N (как очки чародейства). Гибрид — уже есть: ячейки + очки чародейства сосуществуют.
2. **Кулдауны (WoW / MOBA).** Вместо «потрачено до отдыха» — «недоступно N раундов/минут». Для способностей с `recharge=none` кулдаун естественнее, чем ручной возврат.
3. **Кости хитов как валюта (D&D 4e Healing Surges).** У нас кости — лечение на коротком вручную. Полюс: кости — универсальная валюта (потрать кость = активируй способность), тогда короткий отдых — «вернуть половину валюты».
4. **Истощение как трек (Blades Harm / Fate-стресс).** У нас истощение — число 0–6 с формулами-штрафами. Полюс — трек-ячейки с именованными ступенями («вымотан», «сломлен»), каждая со своим эффектом, а не линейным ×2.
5. **Автовосстановление (мобильные игры: энергия по таймеру).** Отдых как кнопка (у нас) vs отдых как время (вернётся через 8 часов игрового времени само). Для кампаний с календарём — второй вариант ложится на `InworldCalendar`.

### 3.9. Финансы: делёж счёта — старая задача

1. **Splitwise.** `per_person | per_table` (как у нас) + «кто за кого заплатил» + упрощение долгов (A должен B, B должен C → A должен C). У нас упрощения нет — долги считаются pairwise по кампании.
2. **Ресторанный POS (iiko).** Стол делится по местам / поровну / по позициям в чеке; неявка = место пустое (не платит). Наш `COUNT(attended)` — вариант «поровну на пришедших»; полюс «по позициям» — разные ставки игрокам (`stake_override` — зачаток).
3. **Подписки (SaaS per seat).** `per_month` (у нас есть тип, но логика заточена под `per_session`) — полный вариант: месячный абонемент покрывает N сессий, пропуск не возвращает деньги, но и не создаёт долг.
4. **`forgiven` как скидка.** У нас прощение гасит долг, но не идёт в заработок. Полюсы: прощение = скидка (идёт в заработок со знаком минус, видна в отчёте) vs прощение = подарок (не видно нигде, как сейчас).
5. **Кассовый vs начисленный учёт.** У нас заработок = `SUM(amount_paid)` по `held` (кассовый). Полюс — начисления по `planned` (дебиторка: «должны столько-то»), оплата гасит. Для календаря оплат нужен второй.

### 3.10. Звук: микшер, а не плеер

1. **Микшеры (Voicemeeter / OBS).** Шины с фейдерами + mute/solo на канал. У нас 4 фиксированные шины с громкостями в `localStorage` — зачаток микшера; полный — mute/solo на Эмбиент/Погоду отдельно.
2. **DAW (Reaper / Ableton).** Сцены/снапшоты микшера + автоматизация (громкость следует за маркером). Наши `sound-sets` + `sceneSwitch` — тот же снапшот; автоматизация — «при переходе сцены холста — сменить сет».
3. **Саундборды (Discord / Stream Deck / Syrinscape).** Пады с хоткеями (у нас 9 + `1-9|QWE`) + банки падов (у нас один набор стингеров; полюс — банки по сценам).
4. **Плееры (Spotify очередь).** Очередь с перетаскиванием + «играть дальше» (у нас очередь плейлиста + shuffle/repeat). Не хватает «добавить следующим» (play next) — за столом частая нужда («а теперь боевую»).
5. **Дакинг в эфире (радио / Discord attenuation).** У нас дакинг 40% на время стингера. Полюс — сайдчейн от микрофона Мастера (приглушать фон, пока говорит) — технически тяжелее, за столом удобнее.

### 3.11. Карты: слои и привязки

1. **ГИС (QGIS).** Слои с порядком, прозрачностью и запросами («показать все ловушки выше 15»). Наши слои фиксированы без порядка/прозрачности. Запросы — аналог фильтра по карте.
2. **Тайловые редакторы (Tiled).** Тайлсеты + слои коллизий отдельно от картинки. У нас коллизий нет; для боёвки с сеткой — понадобились бы (стены блокируют движение/видимость).
3. **Вектор (Figma / Inkscape).** Объекты (двери, ловушки, маркеры) как сущности со свойствами, а не пиксели слоя. У нас двери/ловушки уже полуобъекты; полный вариант — каждый маркер со своей карточкой и связями графа.
4. **`player_visible` как в Roll20/Foundry.** Туман войны + динамическое освещение vs наш флаг целиком на карту. Полюс — видимость по областям/источникам света.
5. **Вложенность (Google Maps zoom-уровни).** `parent_map_id` у нас — зачаток; полный — бесшовный зум регион → поселение → подземелье с наследованием меток.

### 3.12. Холст: от пробковой доски до нодовых редакторов

1. **Пробковые доски (Miro / FigJam / Milanote).** Свободное поле + стикеры + рамки-главы + связи стрелками. Наш холст — почти это; чего нет: лассо-выделение, выравнивание/распределение, шаблоны досок.
2. **Obsidian Canvas.** Ноды-заметки + рёбра + группировка в контейнеры; зум до текста. У нас ноды — ссылки на сущности, а не тексты; полюс — нода с собственным текстом (заметка на холсте без сущности).
3. **Нодовые редакторы (Blender Nodes / Unreal Blueprints).** Типизированные порты + валидация связи («исход проверки не лезет в награду»). Наши 7 видов рёбер без портов — середина между стрелкой Miro и портом Blender. Системные ноды с исходами (из П3) — шаг к портам.
4. **Роадмапы (Jira Timeline / Gantt).** Ось времени поверх графа. Наш `OutsideLink` + сцены-календарь — зачаток; полный — холст с временной линейкой (что за чем в сюжете, а не только что с чем связано).
5. **Версионирование (Figma branches / Git).** У нас undo in-memory; полюс — ветки доски («план А / план Б» развития арки) + снапшоты-версии.

### 3.13. Граф: от генеалогии до соцсетей

1. **Obsidian Graph.** Полный граф + локальный (`focus+depth`, как у нас) + фильтры типов + сила притяжения. У нас нет веса связей и физики раскладки — зато есть тон (`positive|negative|...`), которого в Obsidian нет.
2. **Соцсети (LinkedIn-степени).** «Через 2 рукопожатия», mutual-подсветка. Аналог для кампаний: «как NPC связан с партией через 2 звена».
3. **Генеалогия (FamilySearch).** Строгие типы связей (родитель/супруг) + валидация (нельзя быть своим дедом). Наши `tone/label` свободные; полюс — строгая онтология связей сеттинга.
4. **Матрица смежности (Gephi).** Таблица «кто с кем» вместо графа — для плотных кампаний читаемее графа-паутины.
5. **Визард как dedup-очередь (Tinder для данных / Gmail Priority Inbox).** Наши `exact|likely|doubtful + пошаговое применение` — уже это; полюс — «применить все exact одной кнопкой, doubtful — по одному».

### 3.14. Доступ и послания: секретность без мессенджера

1. **Google Docs «поделиться».** Права на документ (читатель/комментатор/редактор) вместо наших флагов целиком на сущность. Полюс — построчные права на секреты.
2. **Discord-роли и приватные ветки.** Видимость по ролям (партия видит, остальные нет) вместо `player_visible` целиком. Наши `visibilityGrants` — шаг туда.
3. **Передача предметов (MMO-трейд / Among Us-записки).** «Ольга передала амулет — Принять/Вернуть» (уже в спеке оборота карты) — готовый паттерн окна трейда с двумя подтверждениями.
4. **Уведомления без мессенджера (Anki-должники / GitHub-точка).** Наша точка на вкладке «Снаряжение» и загнутый угол карты — из этого семейства: непрочитанное как состояние места, а не как сообщение.

## 5. Локации и зоны (пример владельца 2026-09-05)

Пример от владельца: география в профиле сеттинга была списком, стала колонками Миллера (`LocationMiller.tsx`) — и это кайфово. Теперь задача: локации с зонами. Данж на 25 комнат не должен становиться 26 локациями; районы города — отличные контейнеры для прочих локаций, но считать их самостоятельными локациями не хочется. Районы и комнаты — разные варианты структурирования. Важно и читать, и создавать интуитивно.

### 5.1. Что есть сейчас (факты)

- Модель одна: `setting_locations { setting_id, parent_id, name, kind (свободный текст ≤40), description, ... }`, дерево через `parent_id` (`server/src/routes/settingLocations.ts:115-143`, `:977+` репарент с защитой от циклов, `:102-113` архивация поддерева одним CTE).
- География — колонки Миллера: путь `братья | дети | внуки + превью`, аккордеон ширин, drag-drop переезда, `localStorage geography-millerpath-*`, сортировка `name localeCompare ru numeric` (`LocationMiller.tsx:136-148`). Создание — визард + «Вложенная» из превью (`:687`).
- Карточка локации (`LocationDetailPage.tsx`): табы `Информация | Карта | Вложенность | Обитатели | ...`; вложенность — два поля `childName + childKind` + кнопка (`:401-419`); хлебные крошки по `ancestors`; счётчик в Миллере `focusDescCount` считает ВСЕХ потомков одинаково (`LocationMiller.tsx:202-215`).
- Карта (`LocationMap.tsx`): пины `location_pins`, `MAX_PINS=100`, пины на типы `character|being|location|artifact` с дефолтными цветами; пины — точки, не области.
- `kind` сейчас свободный (`плейсхолдер "континент/город/таверна…"`), поведения от него ноль — только бейдж.

Вывод: район, комната, город и континент — одна сущность одного веса. У комнаты данжа тот же набор таб (статьи, галерея, отношения, важные даты), что у города. Отсюда и боль: 25 комнат = 25 карточек, 25 строк в поиске, 25 в счётчике «Вложенных».

### 5.2. Два кейса — это правда два разных паттерна

| | Район города | Комната данжа |
|---|---|---|
| Штук | 3–7, именованные | 10–30, полунумерованные |
| Однородность | разнородные (внутри — таверны, храмы, рынки) | однородные (комната/коридор/зал) |
| Своя карта | часто да (район можно открыть как карту) | почти никогда (комната живёт на карте данжа) |
| Создание | по одной, вдумчиво | пачкой, списком |
| Порядок | неважен (алфавит ок) | важен (номер/обход) |
| Чтение | «что в районе» (секции) | «план» (таблица/список с краткими заметками) |
| Удаление | переезд содержимого | целиком пачкой |

Одно решение на оба («сделаем все зоны лёгкими») убьёт районы; одно («сделаем все контейнерами») убьёт комнаты. Нужно три веса, а не два.

### 5.3. Как это решали в других областях

1. **Figma: Page → Frame → Group.** Page (мир/сеттинг) содержит фреймы (города/данжи — у фрейма свой холст-карта), внутри фрейма группы (районы — группируют, но своего холста нет) и объекты (таверна, комната). Группа не считается «документом», но её можно в один клик сделать фреймом. Прямой аналог «повысить район до локации».
2. **Discord: Category → Channel → Thread.** Категория (район) — без сообщений, только группирует; канал (локация) — место с содержимым; тред (комната) — лёгкий, создаётся из сообщения в два клика, автоархивируется, по кнопке «превратить в канал». Ключевое: тред НЕ засоряет список каналов.
3. **OpenStreetMap + indoor.** `place=city/district/neighbourhood` — в геокодере; `building → level → room` (indoor mapping) — в геокодер НЕ попадают, ищутся только внутри здания. Наш аналог: комнаты ищутся внутри данжа, а не в глобальном поиске сеттинга.
4. **WoW: Zone → SubZone.** Подзона (Голдшир внутри Элвинна) — только всплывающая подпись, своей карты и separate entity нет. Аналог «комната как подпись на карте данжа».
5. **Revit (BIM): Building → Level → Room.** Комнаты — отдельные объекты, но лёгкие: автонумерация, принадлежат уровню, создаются пачкой, таблица помещений — штатный вид. Удаление уровня тянет комнаты (как наш CTE-архив поддерева).
6. **RimWorld / Oxygen Not Included: зоны краской.** Stockpile-зона — нарисованная область с именем и назначением, не сущность базы. Создаётся мазком, а не формой. Аналог «комнаты рисованием на карте», а не заведением карточек.
7. **Foundry VTT: Scene → Region / Drawing / Wall.** Сцена (данж) — сущность; регионы внутри — геометрия + поведение (темнота, звук), создаются инструментами на холсте пачкой. Наши пины-точки (`MAX_PINS=100`) — зачаток; регионам нужны полигоны, а не точки.
8. **Отели (PMS): Property → Floor → Room.** Этаж — контейнер без бронирования, комната — лёгкая строка (номер, тип, статус), импорт — CSV-списком. Создание 25 комнат — вставка списка, а не 25 форм.
9. **Notion: Page vs inline sub-page + Turn into page.** Подстраница начинается как строчка внутри родителя; когда вырастает — «превратить в страницу» с сохранением истории. Это и есть механика повышения `зона → локация`.
10. **Фотоальбомы: Album → Photo → Face-region.** Альбом (район) группирует; регион лица внутри фото (комната на карте) — лёгкая аннотация с именем, кликабельна, но не фото. Клик по региону открывает кроп, а не карточку.

### 5.4. Предложение: три веса + повышение

- **Локация** (как сейчас, тяжёлая): город, данж целиком, таверна. Полная карточка, участвует в поиске/счётчиках/графе.
- **Область** (контейнер, средний вес): район, этаж, крыло. Группирует, имеет имя+описание, но: не участвует в глобальном поиске как «место», в счётчике «Вложенных» идёт отдельной строкой («Области: 3 · Места: 12»), в Миллере рисуется как секция-заголовок, а не строка. Создаётся одной строкой, переезд drag-drop (уже есть в Миллере) — основной жест.
- **Зона** (лёгкая, встроенная в родителя): комната, стол, пещера. Живёт только внутри родителя: имя + короткая заметка + необязательный пин/полигон на карте родителя. Создаются пачкой (вставка списка 25 строк, автонумерация), показываются на странице родителя компактной таблицей-«планом», а не деревом. В глобальном списке/поиске не светятся (ищутся внутри данжа). По кнопке — **«повысить до локации»** с сохранением имени/заметки/пина (обратное — «понизить до зоны»).

Почему три, а не два: район без своей карты всё равно нуждается в описании и стабильности (его показывают игрокам), а комнате описание из 4000 знаков вредно — туда пишут две строки максимум. Разные формы создания и чтения, общий механизм повышения.

### 5.5. Дешёвый MVP без миграции (на согласование)

1. Договорный словарь `kind` + поведение: `район|этаж|крыло` рисуются как секции, `комната|зал|коридор` — как строки плана. Без новой колонки, только клиент. Проверка: заводит ли словарь путаницу (свободный текст уже привыкли писать как угодно).
2. Вкладка «Вложенность» делится на два блока: «Области» (текущие инпуты) + «План (комнаты списком)»: textarea «по строке на комнату» + кнопка «Добавить N». Комнаты получают `kind=комната` автоматически.
3. Счётчик `focusDescCount` делится: `Области: N · Места: M (из них комнат: K)`.
4. Поиск по географии: опция «искать и в комнатах» (по умолчанию выкл. для глобального, вкл. внутри данжа).
5. Кнопка «повысить до локации» = смена `kind` + тост (настоящее повышение с переносом в отдельную таблицу — только если MVP приживётся).

Дорогое (отдельно, не в MVP): полигоны вместо пинов-точек, рисование зон краской, этажи-уровни с планами, импорт CSV.

Вопросы владельцу:

1. Три веса или достаточно двух (контейнер + место, а комнаты — просто «места с признаком лёгкости»)?
2. Комната ищется глобально или только внутри данжа? (OSM-вариант vs «всё ищется везде»)
3. Повышение «зона → локация» нужно с первого дня или начнём без него и посмотрим, прорастёт ли хоть одна комната?
