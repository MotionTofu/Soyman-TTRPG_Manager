# Зоны локаций — план реструктуризации географии

Дата: 2026-09-06. Репозиторий `E:\Claude\01_Blender` (SoyMan). Основание: `MainWorks/MechaStorm.md`, раздел 5 (разбор 2026-09-05).
Статус: к реализации. Гриллинг по сути пройден в переписке 2026-09-05 — разделы 1–2 фиксируют его итог.

## 0. Коротко: что делаем

У локаций сеттинга появляется тег поведения (вес): **Локация / Сектор / Точка**. `kind` свободный остаётся вывеской («район», «крыло», «караулка»), тег определяет поведение: сектор группирует, но не считается самостоятельным местом; точка живёт внутри родителя, создаётся пачкой, в глобальном поиске не светится (находится через родителя). Зоны — строки той же `setting_locations` (uid, архив, дерево — даром), отдельных таблиц под них нет. Повышение «точка → локация» — копией с backlink, понижения нет.

## 1. Правила репозитория (не обсуждаются здесь)

1. Живая база владельца — только на чтение. Всё, что пишет, проверяется на scratch-паре (`api-scratch-3003` / `client-scratch-5175`).
2. Перед готовностью: `npx tsc -p tsconfig.app.json --noEmit` (из `client/`, без пайпа в `head`) + `npx oxlint src`; счётчик предупреждений не растёт (база: 0 ошибок, 257 предупреждений на 2026-09-05).
3. Критерий «простота для Мастера»: решение страницы, а не человека (блок плана первым на данже, областей — на городе).
4. Ссылка на компендиум — всегда имя рядом с id (правило №8 чарник-плана). Для локаций аналогично: backlink копии — id + имя.

## 2. Зафиксированные решения (молча не пересматривать)))

1. **Три веса, строки одной таблицы.** Отдельной таблицы зон нет: иначе uid/переносимость, архив, дерево, упоминания и граф проектируются заново. Тег — новая колонка (`role`, см. этап 1).
2. **Имена тегов меняются свободно, id — нет.** В коде стабильные id `location | sector | spot`; русские подписи лежат в одном словаре (клиент + сервер симметрично). Переименование подписи — правка словаря без миграции. Вопрос владельца «сможем поменять, когда придут слова» — да, именно так и задумано.
3. **Дерево = где, наполнение = что.** Тайники, секреты, лут, ловушки — контент-строки внутри точки/локации, никогда узлы дерева (`MechaStorm.md`, 5.6.5).
4. **Повышение — копия, не перенос.** Точка остаётся, рядом рождается локация с backlink (`origin_location_id` + имя), на точке бейдж «есть локация». Понижения как операции нет (5.6.4).
5. **Обитатели без дублирования.** Один джойн — одна правда: привязка к точке видна в родителе через существующих вложенных (`?nested=1`, подпись «(Караулка)»). Прямая привязка к родителю независима и переживает удаление точки (5.7).
6. **Поиск находит точки через родителя.** Совпадение с точкой показывает родителя с бейджем, клик открывает родителя с подсветкой строки; прямые попадания ранжируются выше (5.6.6).
7. **Файлы точек — в папке родителя.** Точечные строки папок не получают (`folder_path NULL`), файлы — с префиксом `zone-<id>-`. Требование: надёжно и переносимо между базами (относительные пути едут вместе с родителем).
8. **Вложенность свободная, точки — всегда листья.** Локация и сектор могут содержать любой вес (локация в секторе — норма: поместье в районе); точка ничего не содержит, в ней только наполнение. Тег влияет на поведение, не на право быть родителем.

Эталонный пример (владелец, 2026-09-06): Вотердип (локация) → Северный район (сектор) → Поместье Тролльего черепа (локация) → Второй этаж (сектор) → Комната 12 (точка).

## 3. Модель данных

- `setting_locations.role TEXT NOT NULL DEFAULT 'location'` — `'location' | 'sector' | 'spot'`. Миграция в `server/src/db/db.ts`: `ADD COLUMN` при отсутствии + индекс по `(setting_id, role)` + проверка значения (CHECK или валидация в коде — как принято в проекте, валидацией в `validateLocationPayload`, `server/src/routes/settingLocations.ts:66`).
- `setting_locations.origin_location_id INTEGER NULL REFERENCES setting_locations(id) ON DELETE SET NULL` — backlink копии («создана из точки N»). Имя рядом: при показе бейджа тянем имя одним запросом, не вторым round-trip.
- Новое: `location_content` (наполнение): `id, location_id CASCADE, kind ('secret'|'loot'|'trap'|'feature'), text, created_at`. Лёгкие строки, без файлов и связей. Доступна всем локациям, в UI первым делом — у точек.
- Без изменений (переиспользуется): `being_locations`, `community_locations`, `uid` (миграция `db.ts:2472`), `archiveSubtree` CTE (`settingLocations.ts:102`), репарент с защитой от циклов (`:977+`), упоминания `[[location@uid]]`.

## 4. Этапы

Порядок — по зависимости и по отдаче за столом. Каждый этап самодостаточен и проверяем отдельно.

### Этап 1. Тег поведения на сервере

Цель: роль хранится, валидируется, отдаётся и правится; точки без папок.

- Миграция `role` + индекс; `GET /setting-locations` и `GET /:id` отдают `role`; `POST` принимает `role` (дефолт `location`); `PUT /:id` — смена роли с запретом циклов не требуется (родитель не меняется), но смена `spot → location` молча папку НЕ заводит (папка — только новым отдельным шагом, иначе 25 папок-мусора задним числом); `POST` с `role=spot` — `folder_path NULL`.
- Копирование папок/файлов при смене родителя для точек: двигается только префикс внутри папки родителя (см. `moveEntityFolder`, `server/src/services/vaultPaths.ts`).
- Готово, когда: создание/правка/конвертация роли ходит через API на scratch; `tsc` чисто; старые строки — `role=location` (ничего не изменилось для существующих миров).

### Этап 2. Обитатели: довести вложенных до ума

Цель: семантика «жители точек видны в локации» без дублирования строк.

- Секция «В зонах» на странице родителя видна всегда, когда непуста (сейчас за тумблером `showNestedInhabitants`, `LocationDetailPage.tsx:82`).
- Вложенные сообщества зеркально существам (сейчас запрашиваются только прямые, `settingLocations.ts:269`).
- CTE потомков фильтрует `archived_at IS NULL` (сейчас не фильтрует — архивные зоны поставляют «жителей», `settingLocations.ts:233`).
- Хинт в пикерах точки: «будет виден и в родителе как “(Точка)”».
- Готово, когда: существо, привязанное только к точке, видно на странице данжа с подписью зоны; удаление точки жителя у данжа не отбирает (независимый прямой джойн); архивная точка жителей не поставляет.

### Этап 3. Миллер: секции и точки-листья

Цель: колонки не взрываются; точки не создают колонок.

- Колонка родителя делится: «Секторы» → «Локации» (строки со стрелкой) + свёрнутый блок «Точки · N» (компакт, клик — превью/прокрутка, не колонка). `pick()` на точке ведёт в превью (`showCard`, `LocationMiller.tsx:302`), а не в новую колонку.
- Шапка колонки и превью: делёный счётчик «Области/Секторы: N · Места: M · Точек: K» вместо одного `focusDescCount` (`LocationMiller.tsx:202`).
- Узкий режим (`narrow < 560px`): точки — последним экраном-планом после колонок.
- Готово, когда: данж с 25 точками — одна колонка + блок «Точки · 25», глубина не растёт; drag-drop переезда работает для всех трёх весов с той же защитой от циклов.

### Этап 4. Вложенность: два блока + булк-создание

Цель: «вставь 25 строк — получи 25 точек».

- Вкладка «Вложенность» делится: «Секторы» (текущие инпуты `childName + childKind`) + «План» (textarea «по строке на точку», разбор «Название — заметка», preview «распознано: N», автонумерация опционально, один клик; создаваемые получают `role=spot`).
- Подсказки `kind` по роли (datalist, не валидация): сектору — район/этаж/крыло, точке — комната/зал/коридор. Свободный ввод сохраняется.
- Готово, когда: вставка 25 строк создаёт 25 точек с заметками за один заход; проверка глазами на scratch + повторная вставка не дублирует молча (показывает, что N уже есть, либо создаёт — решает исполнитель, но поведение задокументировано).

### Этап 5. Конвертация существующих (миграционный инструмент)

Цель: старые данжи, нарезанные локациями, переводятся в точки без ручного открытия каждой.

- На вкладке «Вложенность» чеклист детей → действия «Сделать точками» / «Сделать секторами» (один `PUT` на строку, с подтверждением и числом).
- Правило папок: ставшая точкой папку НЕ теряет сразу (файлы не трогаем); новые файлы — уже по правилу префикса. Перенос старых файлов — отдельным шагом только при жалобах (не делать заранее).
- Готово, когда: данж из 25 локаций переводится в точки за два жеста (выбрать всё → подтвердить); отмена — тем же инструментом обратно.

### Этап 6. Таб «План» и наполнение точек

Цель: у точки есть жизнь (описание + обитатели + наполнение), читать — таблицей на родителе.

- Таблица «План» на странице родителя: строки точек (имя, короткая заметка, счётчики обитателей/наполнения), раскрытие строки инлайн, ссылка на карточку точки.
- `location_content` CRUD + UI (тип: секрет/лут/ловушка/особенность + текст). Карточка точки (`LocationDetailPage`) работает как есть (табы обитателей и др.), тяжеловесные табы не урезаем.
- Готово, когда: комната с секретом, лутом, ловушкой и обитателем читается и правится не выходя из данжа; точка без наполнения выглядит как одна строка, а не пустая карточка.

### Этап 7. Поиск через родителя

Цель: «где моя комната» не возникает.

- Глобальный/настроечный поиск: совпадение с `role=spot` возвращает родителя с бейджем («Караулка → Подземелье Н») и подсветкой строки при открытии; прямые попадания выше.
- Визард связей: тот же приём позже (не в этом этапе — только поиск).
- Готово, когда: ввод имени точки предлагает родителя; клик открывает родителя с подсветкой; обычные локации ранжируются как раньше.

### Этап 8. Копия «сделать локацией» + бейдж

Цель: редкое повышение — одним жестом, без потерь.

- Кнопка на точке «Создать локацию из точки»: копия (имя, описание, kind, обитатели-джойны — решением исполнителя, задокументировать), `origin_location_id` → точка, бейдж на точке «есть локация» (id + имя).
- Хронология мира — НЕ в этом этапе, только задел (колонка уже есть и заполняется).
- Готово, когда: из точки рождается локация, точка жива и помечена, связи точки не пострадали.

### Этап 9. Экспорт/импорт и модули
Цель: миры с секторами и точками ездят между базами.

- Экспорт сеттинга включает `role`, `origin_location_id` (через uid), `location_content`; импорт кладёт по uid (`imported.claim("location", ...)` существует, `settings.ts:1823`), уровни вставки — как сейчас (родитель раньше ребёнка, `settings.ts:207`).
- Отношения (`generic_links`) зон по-прежнему не ездят (wontfix П2.7) — зафиксировать в документации этапа, не чинить.
- Готово, когда: круг «выгрузка → разворот в пустую scratch-базу» сохраняет дерево, роли, наполнение и обитателей; отчёт сверки приложен.

### Этап 10. Полотно и граф (маленький, после этапа 7)

Цель: точки не засоряют холст-инструменты, но могут лежать на холсте узлами.

- Палитра/фриформ-поиск холста: совпадение с `role=spot` приходит как родитель с бейджем (та же логика, что этап 7, переиспользовать).
- Граф (`server/src/routes/links.ts`, `NODE_TABLES`): `WHERE role != 'spot'` по умолчанию + тумблер «показывать точки» (в ряд к `DEFAULT_DISABLED`). Единственное место, где допущение «тип = таблица» ломается.
- Нода локации на холсте: бейдж веса (точка красится иначе, чем город). Косметика.
- Отдельных типов нод под точки нет; запрета бросать точки на полотно нет (флоучарт данжа — легальный кейс); миграции старых досок нет (ссылки валидны).
- Готово, когда: поиск палитры предлагает родителя; граф по умолчанию без точек; точка-узел на доске визуально отличима.
