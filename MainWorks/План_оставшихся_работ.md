| zip-статблок (40 ошибок) | `StatblockFormat` не знал `zip_character`/`zip_creature`, хотя модуль дописан. Расширен тип, заведены `zipValue` и два быстрых сохранения, убраны два недостижимых блока `zip_creature` (существо рисуется ранним возвратом, как `dnd_creature`). На сервере zip-форматы добавлены в `JSON_FORMATS` — иначе они оставались без проверки разбора JSON |

### 1.4. Порядок выпуска, когда сборка станет зелёной

По `RELEASE.md` §4:

1. `npm run build` — должен пройти целиком.
2. Коммит версии и `CHANGELOG` отдельным коммитом.
3. `git push origin restore/2026-08-28-simple-tasks`
4. `git push origin restore/2026-08-28-simple-tasks:main` и `git branch -f main origin/main`
5. `git tag -a v2026.9.2 -m "SoyMan_ttrpg 2026.9.2" <хеш коммита версии>` и пуш тега.
6. Дождаться CI (~5 минут, `windows-latest`, Node 22).
7. **Опубликовать черновик — обязательный шаг.** Воркфлоу кладёт релиз черновиком, а черновик `electron-updater` не видит.
8. Проверить `latest.yml` и что в релизе четыре файла.

**Красная линия:** `dist:full` наружу не публикуется — он собирает сид из рабочей базы владельца.

## 2. Результаты гриллинга по U-09 (сделано, зафиксировано для истории)

Разбор шёл 6 кругов, 37 вопросов. Здесь — принятые решения и, что важнее,
**отклонённые варианты с причиной**: без них следующий подход к этой области
начнётся с тех же граблей.

### 2.1. Что вскрыл сам разбор

Два факта, найденные по ходу и изменившие постановку:

1. **Вычисляемый долг уже существовал** — `unpaidSessionsForPlayer` считал
   «ожидалось − оплачено» и показывал игроку в его кабинете. Мастеру не
   показывался нигде. Решение «завести хранимый долг» было принято владельцем
   до того, как этот факт всплыл, и после него переформулировано.
2. **Игрок «Я» (id 19) существовал, но не был ни в одном ростере**, хотя ему
   принадлежат персонажи во всех трёх чужих кампаниях. Из-за этого «я заплатил
   Мастеру» было некуда записать: `session_attendance` хранит строку на члена
   ростера.

### 2.2. Принятые решения

| № | Решение | Отклонённая альтернатива и почему |
|---|---|---|
| Q1 | Дорастить существующую `SessionFinanceModal`, а не заводить новое окно | Новое окно рядом со старым — то самое дублирование, которое разбирает аудит (M-02) |
| Q2/Q8/Q15 | Долг остаётся **вычислением**; хранится только `amount_forgiven` — то, что из чисел не выводится | Хранимый долг разошёлся бы с вычисляемым у игрока при первой правке ставки. Вариант «прощение = проставить `amount_paid`» отклонён: прощённые деньги попали бы в «заработано», то есть починили бы одно враньё вторым |
| Q4/Q12 | Кнопка на герое открывает окно; появляется, только когда время игры наступило | Одно нажатие, ставящее `held` без разбора, воспроизводит исходный дефект: статус есть, денег нет, напоминать больше нечему |
| Q5 | Кнопка лежит **рядом** со ссылкой-героем, не внутри | `<button>` внутри `<a>` — невалидная вложенность, клик уводил бы на страницу сессии |
| Q6/Q13/Q16 | Два исхода; «Не состоялась» просит подтверждения и ставит `cancelled` | Архивация вместо отмены стирает факт, что вечер срывался. Заодно починено меню календаря: выставить `cancelled` существующей игре было нечем |
| Q7/Q14 | Заметка — это `main_events`, предзаполненная и правимая на месте | Третье текстовое поле стало бы двенадцатым местом для текста (M-03). Автоматическая склейка вслепую однажды приклеила бы абзац к тексту, дописанному в соседнем окне — работа в двух окнах здесь штатная |
| Q9/Q18 | Помесячная оплата отложена; в таких кампаниях окно показывает только присутствие | Делить месячную ставку на число игр месяца — менять сумму задним числом при каждой новой игре месяца |
| Q10 | Просрочена — `planned` и **время начала** прошло | Сутки форы — приложение решает за Мастера, когда ему разбираться |
| Q11/Q17/Q27 | Меню и карточка сессии ведут в окно; пульт — по настройке, умолчание «в плашку». Заведена вкладка «Пульт сессии» | Пульт закрывают, когда игра только кончилась и все расходятся: окно с деньгами там поперёк |
| Q19/Q28 | Плашка — список строк, под героем, до «Кампаний», только Мастеру | Над героем — бухгалтерия встаёт между Мастером и подготовкой; одна строка со счётчиком лишает выбора, с какой игры начать |
| Q20/Q23 | **Метки в календаре Главной не добавлять** | Плашка висит в паре сантиметров и называет те же игры — третий способ сказать одно и то же (§1.10). В календаре кампании метка нужна: там плашки нет |
| Q21 | Для `held` окно — правка задним числом: другой заголовок, без кнопок исхода | Кнопка «Состоялась» на состоявшейся — пустышка или ловушка |
| Q22/Q30 | Долг виден в профиле игрока и в составе кампании; действия — только в самой сессии | «Погасить вообще» заставило бы приложение выбрать сессию за Мастера |
| Q24/Q25/Q31 | Отменённые нумеруются отдельно: `4, 5, 6, Отменённая №1, 7`. Подзапрос номера сведён из четырёх роутов в один | «Сессия №7 (отменена)» читается как седьмая игра, которую заодно отменили — смешение двух нумераций |
| Q26 | При отмене суммы не стираются; диалог выводится, **только если** что-то внесено | Молча стирать нельзя; спрашивать всегда — диалог в редчайшем случае |
| Q29 | Прощение: кнопка «остаток» плюс правимое поле | Только кнопка — списание задним числом нечем поправить; только поле — за столом нужен один клик |
| Q32/Q34/Q36 | «Я» возвращается в ростеры разовой идемпотентной починкой по правилу «есть персонаж — значит участник» | Отдельное поле «моя оплата» завело бы вторую денежную модель рядом с существующей |
| Q33 | Кнопки «в пульт» на герое **нет** | Клик по герою обещает «иду готовиться»; две кнопки превращают одно обещание в развилку. Пульт уже в одном клике из навигационного виджета |
| Q35/Q37 | Свой расход виден в профиле «игроцкой» кампании и строкой в плашке; ставки владелец проставляет сам | «Потрачено» рядом с «заработано» на Главной превращает витрину заработка в бухгалтерский баланс (§1.12) |

### 2.3. Что осталось незакрытым после этой работы

- **Ставки в трёх «игроцких» кампаниях не проставлены** (`payment_type = 'free'`,
  `session_rate = 0`). Пока их нет, механизм долга там считает ноль и
  напоминалка не сработает. Это разовая настройка владельца — приложение
  ставку взять неоткуда.
- **Герой при «5 / 5 готово»** по-прежнему показывает чек-лист, когда онбординг
  завершён, а ближайшей игры просто нет. Разобрано, что причина — один блок на
  два несвязанных состояния («ты ещё не начал» и «следующая игра не
  назначена»), но решение не принято.

враньё интерфейса: кнопка «Отменить» есть, а отмены нет.

### 6.1. «Отменить» не отменяла — починено

`SessionDetailPage.tsx` и `CampaignDetailPage.tsx` передавали
`restoreFn: () => api.del(…)` — то есть **повторный `DELETE`**. Но удаление на
сервере это `UPDATE … SET archived_at = datetime('now')`
(`sessions.ts:259`, `campaigns.ts:334`), поэтому второй `DELETE` просто
переписывал дату, и сущность оставалась в архиве. Нажатие «Отменить»
возвращало 200 OK и не делало ничего.

Обе переведены на `PUT /:id/restore` (`archived_at = NULL`) — эндпоинты
существовали всё это время.

### 6.2. Тост умирал вместе со страницей — починено

Состояние жило в самой странице, и тост рисовался её же разметкой. Но
удаление сессии, кампании и персонажа заканчивается `navigate(…)`: страница
размонтировалась, унося тост. В `CampaignDetailPage` он к тому же **не был
отрисован вовсе** — `undoToast` получали из хука и не использовали.

`useUndoDelete` переписан на контекст: `UndoDeleteProvider` живёт в `AppShell`,
тост висит поверх новой страницы все 8 секунд. Заодно ушла четырёхкратная
копия одной и той же разметки тоста.

Проверено живьём (scratch-база, порт 5174): архивация кампании → тост виден на
`/campaigns` после перехода; архивация локации → `DELETE …/611` → 200, клик
«Отменить» → `PUT …/611/restore` → 200, локация вернулась в дерево.

### 6.3. У дерева локаций была своя, отдельная отмена — сведена к общей

`LocationTree.tsx` держал собственный механизм: состояние `lastArchived`,
карточка с кнопкой «Восстановить» вместо тоста с «Отменить», **без таймера** —
висела, пока не закроешь. Ровно то дублирование, которое разбирает аудит
(M-02): два способа сказать одно и то же, в двух разных видах. Переведена на
общий механизм.

### 6.4. Изображение галереи — undo невозможен без серверной работы

`galleryRouter.delete` (`gallery.ts:169`) делает
`DELETE FROM gallery_images` — строки больше нет, а файл ушёл в архив
хранилища либо стёрт совсем (`removeOrArchive`). Отмена потребовала бы нового
эндпоинта: пересоздать запись и вернуть файл. Это новое поведение, а не
правка, — значит `grilling` и решение владельца. **Не сделано намеренно.**

### 6.5. Мёртвый код: три функции удаления, которые никто не зовёт

В `SettingDetailPage.tsx` объявлены и **нигде не вызываются**:

- `deleteBeing` (`:1666`) — архивация личности,
- `deleteBeing` (`:1924`) — архивация записи бестиария,
- `deleteCommunity` (`:2076`) — архивация сообщества.

То есть из списков сеттинга удалить существо или сообщество нечем: только с
детальной страницы. Либо кнопки потерялись при какой-то правке, либо так и
задумано — но тогда функции надо убрать. Undo в них не добавлялся: незачем
чинить то, что не вызывается.

### 6.6. Нативные `confirm()` вместо `useConfirm`

`CommunityDetailPage.tsx:114` и `EntryImagesTab.tsx:135` спрашивают
подтверждение системным окном браузера, а не диалогом приложения, как везде
ещё. За столом это выглядит чужеродно и не следует теме. Не чинилось — вне
объёма Фазы 2.1.

### 6.7. Порядок проверки в живом приложении

Dev-серверы `client`/`api` на 5173/3001 смотрят в рабочую базу владельца.
Проверка велась на `client-scratch` (5174) + `api-scratch-alt` (3002) —
отдельная `server/data-scratch`. Заведённые для проверки записи (три локации
в Рейвенлофте, две кампании в `data-scratch-3003`) удалены после работы;
чужого не тронуто.

Оговорка: локацию **нельзя удалить насовсем через API** — `DELETE` только
архивирует, `DELETE FROM setting_locations` в коде сервера нет вовсе. Свои
тестовые записи пришлось убирать прямо из scratch-базы. Для Мастера это
значит, что архив локаций растёт и вычистить его изнутри приложения нечем.
