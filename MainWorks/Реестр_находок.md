## 1. F-01 · Проверка типов клиента была фикцией

**Статус:** починено 2026-09-03 · **Важность:** наивысшая из всех записанных.

Проверки клиента шли командой `npx tsc --noEmit -p tsconfig.json`. Но
`client/tsconfig.json` — солвент-конфиг: `"files": []` и одни `references`. Он
**не проверяет ни одного файла и всегда возвращает 0**. Правильная команда —
`tsc -b`.

Из-за этого в ветке накопилось **68 ошибок TypeScript в 13 файлах**, и все
проверки всё это время рапортовали успех. Серверные проверки были настоящими
(`include: ["src"]`), поэтому расхождение никто не замечал.

Рядом та же ловушка, уже записанная в `CLAUDE.md`: `npx tsc … | head`
возвращает код `head`, а не компилятора.

**Что делать впредь:** клиент проверяется только `tsc -b`, без пайпа.

## 2. F-02 · «Отменить» возвращала 200 OK и не отменяла

**Статус:** починено 2026-09-03 · коммит `253caa1`

`SessionDetailPage.tsx` и `CampaignDetailPage.tsx` передавали в хук
`restoreFn: () => api.del(…)` — то есть **повторный `DELETE`**.

Но удаление на сервере — это не удаление:

```
sessions.ts:259    UPDATE sessions  SET archived_at = datetime('now') WHERE id = ?
campaigns.ts:334   UPDATE campaigns SET archived_at = datetime('now') WHERE id = ?
```

Второй `DELETE` просто переписывал дату новой. Сущность оставалась в архиве,
запрос возвращал 200 OK, интерфейс показывал успех. Отмены не происходило
никогда.

Эндпоинты `PUT /:id/restore` (`archived_at = NULL`) существовали всё это
время — их просто не звали. Обе страницы переведены на них.

**Чем опасен класс:** дефект неотличим от работы. Запрос успешен, ошибок нет,
проверить можно только глазами на следующем экране.

## 10. F-12 · Системные окна браузера · починено

**Статус:** починено 2026-09-03, коммит `f53c594`. Было **50** нативных
вызовов в 32 файлах при 65 уже переведённых. Стало **0**.

Первоначальная цифра в этом реестре (52) была завышена: `grep` не отличал
`window.confirm` от `confirm(...)` хука. Признак точный — `useConfirm`
возвращает Promise, поэтому его вызов всегда с `await`.

### Почему это не косметика

В `electronApi.ts` живёт патч `installNativeDialogFocusFix`, и его комментарий
объясняет цену вопроса: после нативного диалога Windows не возвращает фокус
webContents — «в поле курсор стоит, а буквы не появляются», помогает только
переключиться на другое окно и обратно. Патч поставили на сам
`window.confirm`, «а не на каждый из девяноста вызовов».

Теперь для `confirm` первопричины не осталось. Плюс системное окно блокирует
процесс целиком и не следует ни теме, ни шрифтам приложения — за столом это
хуже диалога внутри окна.

### Заодно ушёл текст, который ничего не говорил

«Вы уверены, что хотите удалить ЭТО?» стоял в двадцати с лишним местах. Теперь
диалог называет предмет разговора: «Удалить атаку «Укус»?», «Убрать «Огненный
шар» из списка заклинаний?», «Удалить главу вместе с её текстом?», «Убрать
чувство «Тёмное зрение»?».

Где имя недоступно — текст называет хотя бы род: «Удалить задачу?», «Удалить
напоминание?», «Удалить заметку о связи?», «Убрать участника из очереди хода?».

## 13. F-16 · Пять ошибок линтера · починено

**Статус:** починено 2026-09-03. `npx oxlint src` теперь даёт **0 ошибок** —
впервые за всё время работы по этой ветке.

Оба случая — хуки под условием, класс дефекта, который однажды уже ронял
раздел.

**`InworldCalendar.tsx`.** `useRef` для долгого нажатия стоял **после** раннего
возврата `if (months.length === 0) return <p>Календарь сеттинга не настроен.</p>`.
При ненастроенном календаре компонент выходил до этого хука — два хука; как
только месяцы приходили — три. React получал другой порядок между рендерами.
`useRef` поднят выше возврата.

Проверено живьём на обеих ветках: сеттинг без календаря (Рейвенлофт) рисует
«Календарь сеттинга не настроен», сеттинг с календарём (id 1) рисует все
двенадцать месяцев и сетку дней. Ошибок React о порядке хуков в консоли нет.

**`litm/ThemeCard.tsx`.** В `ThemeKitPicker` строка `if (!isOpen) return null`
стояла **перед** тремя `useState` и `useEffect`. Закрытая модалка — ноль хуков,
открытая — четыре. Хуки подняты выше возврата; чтобы закрытая модалка при этом
не грузила справочник, в эффект добавлен ранний выход `if (!isOpen) return`, а
`isOpen` — в зависимости. Сам `return null` перенесён вниз, после хуков.

## 14. F-17 · `narrativeCallbacks` восстановлены

**Статус:** починено 2026-09-03, **но числами не подтверждено** — см. оговорку.

`MentionTextarea` объявлен через `memo` (`MentionTextarea.tsx:53`), однако
`onChange` собирался заново на каждый рендер прямо в разметке:

```
onChange={(v) => setDraftDossier({ ...draftDossier, [dossierKey]: v })}
```

Новая ссылка на функцию при каждом рендере означает, что `memo` не работал
вовсе: нажатие клавиши в «Идеалах» перерисовывало и «Черты характера», и
«Привязанности», и «Слабости».

Восстановлено не тем способом, каким было в `wip`: колбэки берут прежнее
состояние через функциональный сеттер
(`setDraftDossier((prev) => …)`), поэтому у `useMemo` **пустые зависимости** и
ссылки стабильны на всю жизнь компонента. Вариант с `[draftDossier]` в
зависимостях выглядел бы мемоизацией, но пересоздавал бы колбэки на каждый
набранный символ — то есть не дал бы ничего.

**Оговорка.** Замер счётчиком рендеров не сделан: в scratch-базе у персонажей
не открылся лист D&D — сессия отвалилась после перезапуска API-сервера, а
пароль вводить нельзя. Правка верна по построению, но правило «гипотеза без
замера не годится» требует числа. Замерить, когда лист будет открыт.

## 19. F-27 · Дублирующиеся ключи `day` в React

**Статус:** открыто · источник не найден

В консоли при открытии «Хроники мира» сеттинга с настроенным календарём:

```
Encountered two children with the same key, `day`
```

Повторяется на каждый рендер. React предупреждает, что такие дети могут
дублироваться или пропадать — то есть день календаря может визуально
потеряться.

Единственное место, где ключ строится из дня, — `InworldCalendar.tsx:163`
(`key={c.day}`), и там значения уникальны: пустые ячейки идут как
`empty-${i}`, дни — числами 1…N. Поиска по `key="day"` в `src/` не даёт ничего.
Значит ключ собирается где-то динамически; искать надо с React DevTools по
дереву в момент предупреждения.

Найдено попутно при проверке F-16, к ней не относится.

## 20. F-28 · Фильтр категорий справочника недостижим

**Статус:** ждёт решения владельца · переформулировка F-14

Это то, чем F-14 оказалась на самом деле.

Ветка `if (isMechanicsSection)` в `CompendiumSection` (строки 1205–1333)
заканчивается **`return`**. Всё, что стоит ниже и снова проверяет
`isMechanicsSection`, для справочника не исполняется никогда:

| строка | что там |
|---|---|
| 1448 | блок при `topLevel.length > 0` |
| 1472 | ещё один блок |
| 1478–1502 | **кнопки фильтра по категориям** — «Все · N», «Магические эффекты · 6» |
| 1729–1745 | ветка отображения с учётом `mechanicsCategoryFilter` |

Проверено живьём: в справочнике D&D 5.5 категории рисуются заголовками групп,
а **кнопок фильтра в DOM нет вовсе**.

То есть фильтр по категориям написан, но подключить его забыли — ровно класс
«объявлено, но не подключено» (§7.2 плана). И `mechanicsCategoryFilter`
читается только отсюда, из недостижимого кода.

**Развилка:**

- **Подключить** — перенести кнопки фильтра внутрь ветки 1205–1333, до
  `return`. Мастер получит быстрый отбор по шести категориям; в справочнике
  D&D 5.5 их 589 записей, так что польза заметная.
- **Удалить** — убрать недостижимые фрагменты вместе с состоянием. Категории
  уже видны свёрнутыми блоками `<details>`, и это может считаться достаточной
  навигацией; тогда фильтр — второй способ делать то же (M-02).

Кодом не начинать: выбор за владельцем.

## 23. F-31 · Подтверждение, которое не подтверждало

**Статус:** починено 2026-09-03, коммит `f53c594`

`ModulesTab.tsx:111` вызывал `confirm({...})` от `useConfirm` **без `await`**:

```
if (!confirm({ title: …, message, … })) return;
```

`confirm` возвращает Promise — всегда истинный, поэтому `!promise` всегда
ложно, `return` не срабатывал никогда. Модуль удалялся **что бы Мастер ни
ответил**, а диалог оставался висеть уже поверх свершившегося факта.

Найдено при сплошном переводе на `useConfirm`. Проверены все 65 вызовов —
случай единственный.

Класс тот же, что у F-02: дефект неотличим от работы. Диалог показан, кнопки
нажимаются, ошибок нет — только результат не зависит от ответа.
