# UI-конвенции

Единый стандарт для всех detail-страниц сущностей (Кампания, Персонаж, Сеттинг, Локация,
Существо, Община, Артефакт, Игрок, Сессия и будущих). Цель: открыв любую новую сущность,
пользователь не должен заново привыкать к интерфейсу. Новый код и правки существующих
страниц должны следовать этому документу; расхождения со старым кодом чинятся по мере
доработки соответствующей страницы (см. план унификации).

## 1. Хлебные крошки

Каждая detail-страница сущности, у которой есть родитель в иерархии (Локация → Сеттинг,
Существо → Сеттинг, Персонаж → Кампания, Сессия → Кампания и т.д.), начинается с
единой строки хлебных крошек над заголовком:

```
Сеттинг / Регион / Город / Таверна
```

- Компонент: `<Breadcrumbs items={[...]} />` (общий, не дублировать вручную по страницам).
- Стиль: `row muted`, разделитель — `" / "`, последний элемент — не ссылка (текущая страница).
- Показывает полный путь от корня (Сеттинг/Кампания) до текущей сущности, включая всех
  промежуточных предков (например, вложенные локации/сообщества).

## 2. Заголовок сущности и её переименование

- Заголовок — всегда `<h1>`, без `onDoubleClick`.
- Переименование — маленькая иконка-кнопка `✎` сразу справа от `h1`, открывающая
  inline-редактирование имени (текстовое поле + «Сохранить»/«Отмена» рядом). Никакого
  double-click и никакого «разворачивания всей карточки в форму» ради смены одного имени.
- Правее, в `entity-header-actions`, идут остальные действия сущности в фиксированном
  порядке: обычные действия → «Архивировать» (`button.danger`) всегда последней.

## 3. Редактирование содержимого

- Любое отдельно стоящее текстовое поле — через `EditableTextCard` (просмотр →
  «Редактировать» → форма → «Сохранить»/«Отмена» → снова просмотр). Не изобретать
  отдельный `editMode`, разворачивающий сразу несколько полей в одну форму.
- Если полей у карточки несколько и они логически не одно целое — несколько соседних
  `EditableTextCard`, а не один общий переключатель режима для всех сразу.

## 4. Вкладки

- Вкладки detail-страницы всегда синхронизированы с URL через общий хук `useTabState`
  (обёртка над `useSearchParams`), а не голый `useState`. Это даёт: сохранение вкладки
  при обновлении страницы, работу кнопки «назад» в браузере, возможность дать прямую
  ссылку на конкретную вкладку.
- Порядок вкладок: главное содержимое/статблок → тематические разделы сущности →
  «Связи» (если вынесены в отдельную вкладку — не обязательно всегда) → «История»/
  «Ход игры» (если применимо к сущности) — последними.
- «Связи» — либо отдельная предпоследняя вкладка, либо (для более простых сущностей)
  `LinkDropZone` прямо в основной вкладке — выбор фиксируется один раз на тип сущности
  и не должен быть случайным.

## 5. Бейджи и статусы

- `.badge.planned/.held/.cancelled/.rescheduled` — **только** для статусов сессий/событий
  календаря. Не переиспользовать эти классы для тегов вроде «тип локации» или
  «категория существа».
- Для некалендарных ярлыков (тип/категория/тег) — нейтральный `.badge.tag`
  (акцентный/серый цвет, не пересекающийся по смыслу со статусами).

## 6. Иконки

- В основном интерфейсе иконки — не эмодзи (эмодзи рендерятся по-разному на разных ОС
  и не позволяют управлять цветом/размером). Для действий (добавить/удалить/архивировать/
  связи/карта и т.п.) — единый набор SVG-иконок или, до появления такого набора,
  обычный текст без иконки. Не добавлять новые эмодзи-кнопки.

## 7. Визуальная идентичность сущности

- Рядом с `h1` — небольшой цветной `entity-type-chip` с названием типа сущности
  («Локация», «Существо», «Артефакт» и т.д.). Цвет чипа переиспользуется в
  хлебных крошках, в результатах поиска (`SearchPanel`) и в карточках связей — один
  цвет = один тип сущности везде в интерфейсе.
- Полноразмерный фон (`campaign-bg-layer` / `setting-card-bg`) остаётся только у
  Кампании и Сеттинга — это осознанное решение, не тиражировать на другие сущности.

## Уже устоявшиеся паттерны (эталон, тиражировать без изменений)

- List-страницы верхнего уровня (Кампании/Игроки/Сеттинги/Ресурсы): `h1` + «+ Новое X»
  (`button.primary`) справа в шапке → `grid-cards` из `Link.card` → `Modal` создания.
- Архивирование: `confirm("Отправить <сущность> в архив?")` → `DELETE`, кнопка
  «Архивировать» (`button.danger`) последней в `entity-header-actions`.
- `generic_links` + `LinkDropZone`/`SEARCH_DRAG_MIME` — универсальный drag&drop-механизм
  связей между любыми сущностями, используется как основа для «Связи» везде.
