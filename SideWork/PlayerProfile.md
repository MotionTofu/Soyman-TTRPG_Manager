## 1. Графический дизайнер-перфекционист

### 1.1 Нет заголовка страницы с плашкой-инверсией (§1.4) — `PlayerDetailPage.tsx:165`

**Было:** `<h1>{player.name}</h1>` — просто текст.

**Должно быть:** Плашка-инверсия (§1.4) — шапка карточки с инвертированным фоном, как у `CreatureCard` (шаг 4 ревизии). Имя игрока — это заголовок карточки, и он должен вести себя как плашка: `background: var(--ink)`, `color: var(--paper)`, без радиусов (§1.1).

**Критичность:** Высокая. Нарушение фундаментального правила системы: «Шапка карточки — плашка-инверсия, а не жирный текст» (§1.4).

### 1.2 Аватар 228×228 без адаптации — `index.css:4271`

```css
.player-avatar {
  width: 228px;
  height: 228px;
  ...
}
```

На экране 860px аватар занимает 26% ширины. На 390px — 58%. Нет `max-width: 100%` или медиазапроса. На узких экранах аватар вылезает за пределы карточки или сжимает содержимое.

**Решение:** добавить `max-width: min(228px, 100%)` или `@media (max-width: 600px) { .player-avatar { width: 120px; height: 120px; } }`.

### 1.3 `roster-avatar-placeholder` без стиля для 228px — `PlayerDetailPage.tsx:153`

Плейсхолдер аватара использует класс `roster-avatar roster-avatar-placeholder`, но `roster-avatar` определён для списков (маленький размер), а 228×228 задаёт `player-avatar`. Результат: плейсхолдер имеет размер из `roster-avatar` (вероятно, 32-48px), а не 228×228.

**Критичность:** Средняя. Визуально ломает компонент при отсутствии аватара.

### 1.4 `borderLeft: "3px solid var(--accent)"` на напоминаниях — `PlayerHomePage.tsx:78,106`

Нарушение §1.3: «Обводка одной толщины: 1 px по всему контуру». 3px — это в три раза толще. Акцентная обводка слева — приём, которого нет в design_revision.md.

**Критичность:** Средняя. Визуально выбивается из системы.

### 1.5 `borderRadius: 6` на изображениях — `PlayerCampaignPage.tsx:199`

```tsx
<img src={img.image_url} alt={img.caption} style={{ maxWidth: "100%", borderRadius: 6 }} />
```

Нарушение §1.1: «Радиусов нет. Система рисует прямой угол.» Исключение — только пользовательская настройка (§4), и то только для внешнего угла карточки.

**Критичность:** Средняя. Нарушение инварианта.

### 1.6 `h3` без плашки — `PlayerDetailPage.tsx:182,244,288`

Заголовки секций «Доступ к игрок-клиенту», «Группы игроков», «Персонажи» набраны просто `<h3>`. По §1.4, подпись секции — капс на разделителе 1.5 px, а не жирный текст.

**Критичность:** Средняя. Иерархия нарушена.

### 1.7 PlayerCabinetPage: `<h1>Кабинет</h1>` — служебная надпись

Как «Главная» была снята за служебную (ревизия шаг 1), так и «Кабинет» — тоже. Имя страницы должно либо отсутствовать (как на главной), либо быть плашкой-инверсией.

**Критичность:** Низкая.

## 2. Программист

### 2.1 Пароль виден в DOM после ввода — `PlayerDetailPage.tsx:219`, `PlayerCabinetPage.tsx:175`

```tsx
<input type="password" ... />
```

`type="password"` маскирует ввод, но `autoComplete` по умолчанию разрешает браузеру сохранять пароль. После отправки формы пароль остаётся в `localStorage` браузера (автозаполнение). На.shared/computer это утечка.

**Решение:** добавить `autoComplete="new-password"` (при создании) или `autoComplete="current-password"` (при смене).

**Критичность:** Критично (безопасность).

### 2.2 Нет валидации пароля на клиенте — `PlayerCabinetPage.tsx:79-106`

`changePassword()` проверяет только совпадение и непустоту. Нет проверки длины (минимум 6-8 символов), сложности. Сервер может отклонить, но пользователь увидит сырую ошибку API.

**Решение:** добавить проверку длины перед отправкой.

**Критичность:** Высокая.

### 2.3 Дублирование логики загрузки аккаунта — `PlayerDetailPage.tsx:36-45`

`refreshAccount()` делает `GET /auth/players` и ищет по `player_id`. Это повторяет логику, которая могла бы быть в `useCurrentUser` или отдельном хуке. При добавлении третьего места с такой логикой — три копии.

**Решение:** вынести в `usePlayerAccount(playerId)` хук.

**Критичность:** Средняя.

### 2.4 `maxWidth: 400` захардкожен — `PlayerCabinetPage.tsx:156`

```tsx
<div className="card stack" style={{ maxWidth: 400 }}>
```

На экране 1920 карточка пароля будет 400px слева. На 390 — те же 400px, но контейнер уже, и `maxWidth` не срабатывает (面板 уже 400px). Нет в CSS, нет в дизайн-системе.

**Решение:** перенести в CSS как `.cabinet-password-card { max-width: 400px; }` или ограничить через `min(400px, 100%)`.

**Критичность:** Средняя.

### 2.5 Inline стили вместо CSS-классов — `PlayerDetailPage.tsx:248-265`

```tsx
style={{
  display: "flex",
  flexWrap: "wrap",
  gap: 8,
  marginTop: 4,
  padding: "4px 8px",
  borderRadius: "var(--card-radius)",
  border: `1px solid ${isIn ? "var(--accent)" : "var(--line)"}`,
  ...
}}
```

15+ inline стилей для одного элемента. Нарушение DRY, невозможно переиспользовать, невозможно переопределить через CSS.

**Решение:** вынести в `.player-group-chip` и `.player-group-chip.active`.

**Критичность:** Средняя.

### 2.6 Нет `aria-label` на кнопку загрузки аватара

`<label className="avatar-upload-label">` — кнопка без текста (скрытый `<input type="file">`). Скринридер не поймёт, что это кнопка загрузки. `title={IMAGE_HINT}` на `<label>` — не `<button>`, aria-атрибуты не наследуются.

**Решение:** добавить `role="button" aria-label="Загрузить аватар"` на `<label>`.

**Критичность:** Средняя (a11y).

### 2.7 `confirm()` вместо кастомной модалки — `PlayerDetailPage.tsx:126,140`

```tsx
if (!confirm("Отправить персонажа в архив?")) return;
if (!confirm("Отправить игрока в архив?")) return;
```

`confirm()` — блокирующий вызов, не стилизуется, не переведётся, выглядит как системный диалог ОС. В приложении есть компонент модалки (`.modal-backdrop`).

**Критичность:** Критично (UX).

### 2.8 Нет optimistic UI

При переключении группы (добавление/удаление из `playerGroupIds`) пользователь ждёт ответа сервера. При 200ms задержке это незаметно, но при сетевой проблеме — кнопка «мертвая» без обратной связи.

**Решение:** оптимистично обновить `playerGroupIds` до ответа сервера, откатить при ошибке.

**Критичность:** Средняя.

### 2.9 `useEffect` с `id` в deps, но `refresh()` вызывается внутри — `PlayerDetailPage.tsx:101-110`

```tsx
useEffect(() => {
  refresh();
  refreshAccount();
  ...
}, [id]);
```

`refresh()` определена внутри компонента, но не в deps. ESLint `react-hooks/exhaustive-deps` отключён (`// eslint-disable-next-line`). Это намеренно, но `refresh` пересоздаётся при каждом рендере, и если `id` не меняется — эффект не перезапускается, но `refresh` мог бы вызваться вручную.

**Критичность:** Низкая.

### 2.10 Нет `AbortController` в `PlayerDetailPage` — `PlayerDetailPage.tsx:101-110`

В `PlayerHomePage.tsx:53` есть `AbortController`, в `PlayerDetailPage` — нет. При быстром переключении между игроками старые запросы завершатся последним `setPlayer`, но могут вызвать гонку данных (race condition).

**Решение:** добавить `AbortController` с cleanup.

**Критичность:** Средняя.

## 3. Придирчивый пользователь

### 3.1 НУ КАК ЭТО нет подтверждения при архивации игрока?! — `PlayerDetailPage.tsx:140`

```tsx
if (!confirm("Отправить игрока в архив?")) return;
```

Одно нажатие — и игрок архивирован. Нет второго шага, нет предупреждения «это удалит всех персонажей игрока», нет undo. `confirm()` — это 1990-е. Придирчивый: «А если я задел не того?!»

**Решение:** модалка «Вы уверены? Это архивирует [Имя игрока] и его [N] персонажей. Отмена / Архивировать».

```tsx
async function saveEdit() {
```

## План исправлений

### Фаза 1: Критично (безопасность + ломающие UX)

Цель фазы: убрать три ситуации, где пользователь может **сломать что-то одним нажатием** и **не получить обратной связи**.

---

#### Шаг 1. autoComplete для паролей

**Где:** `PlayerDetailPage.tsx:219` и `PlayerCabinetPage.tsx:175`

**Что делаем:** На все `<input type="password">` добавляем атрибут `autoComplete`:
- При **создании** нового аккаунта: `autoComplete="new-password"` — браузер не будет предлагать сохранить пароль, которого ещё нет.
- При **смене** пароля: `autoComplete="current-password"` для текущего поля и `autoComplete="new-password"` для нового.

**Почему важно:** Сейчас браузер может предложить «Сохранить пароль?» после создания аккаунта. Если компьютер общий — пароль останется в автозаполнении. С `autoComplete="new-password"` браузер это проигнорирует.

---

#### Шаг 2. Модалка подтверждения вместо confirm() при архивации игрока

**Где:** `PlayerDetailPage.tsx:139-143`

**Что делаем:**
1. Добавляем состояние `const [showArchiveModal, setShowArchiveModal] = useState(false)`.
2. Кнопка «Архивировать» вызывает `setShowArchiveModal(true)` вместо `confirm()`.
3. Рендерим модалку (компонент `Modal` или `<div className="modal-backdrop">` с содержимым):
   - Заголовок: «Архивировать игрока?»
   - Текст: «Это архивирует [Имя игрока] и его [N] персонажей. Игрок потеряет доступ к приложению.»
   - Две кнопки: «Отмена» (закрывает модалку) + «Архивировать» (красная, выполняет `api.del` + `navigate`).
4. Счётчик персонажей берём из `player.characters.length`.

**Почему важно:** Сейчас одно неосторожное нажатие — и игрок архивирован. Модалка даёт секунду на раздумье и показывает последствия.

---

#### Шаг 3. Модалка подтверждения вместо confirm() при смене роли

**Где:** `PlayerDetailPage.tsx:47-52`

**Что делаем:**
1. Добавляем состояние `const [showRoleModal, setShowRoleModal] = useState(false)`.
2. Кнопка «Забрать метку «Мастер»» / «Сделать мастером» вызывает `setShowRoleModal(true)`.
3. Модалка:
   - Заголовок: account.role === "gm" ? «Забрать метку Мастер?» : «Сделать мастером?»
   - Текст: «[Имя] сможет [赶готовить сессии / только участвовать в играх].»
   - Две кнопки: «Отмена» + подтверждение.

**Почему важно:** Смена роли — необратимое действие (мастер теряет доступ к пульту, игрок — к редактированию). Без модалки это одна кнопка без объяснения.

---

#### Шаг 4. Индикатор загрузки при сохранении

**Где:** `PlayerDetailPage.tsx:131-137` (saveEdit) и `PlayerCabinetPage.tsx:72-77` (saveName)

**Что делаем в `PlayerDetailPage`:**
1. Добавляем `const [saving, setSaving] = useState(false)`.
2. В `saveEdit()`:
   ```tsx
   async function saveEdit() {
     if (!nameDraft.trim() || !player) return;
     setSaving(true);
     try {
       await api.put(`/players/${id}`, { name: nameDraft, notes: notesDraft });
       syncMentionLinks(...);
       setEditing(false);
       refresh();
     } finally {
       setSaving(false);
     }
   }
   ```
3. На кнопках «Сохранить» и «Отмена»:
   ```tsx
   <button className="primary" onClick={saveEdit} disabled={saving}>
     {saving ? "Сохранение…" : "Сохранить"}
   </button>
   <button onClick={() => setEditing(false)} disabled={saving}>Отмена</button>
   ```

**То же самое** для `PlayerCabinetPage.saveName()`.

**Дополнительно** для смены пароля (`PlayerCabinetPage.changePassword`): там уже есть `passwordSaving` — проверяем, что кнопка «Сменить пароль» использует его для `disabled` (сейчас `disabled={passwordSaving}` уже есть — ок).

**Почему важно:** Без этого пользователь может нажать «Сохранить» пять раз, получить пять запросов, и не понять — сохранилось или нет.

```tsx
<img src={c.avatar_image_url} alt={`Аватар ${c.character_name}`} className="roster-avatar" />
```

**Зачем:** Экранные ридеры читают `alt=""` как «изображение без описания». С `alt="Аватар Алексей"` пользователь скринридера понимает, что это фото персонажа.

#### Шаг 5. Оптимистичное обновление групп (2.8)

**Где:** `PlayerDetailPage.tsx:280-288`

**Было:**
```tsx
onChange={async () => {
  if (isIn) {
    await api.del(`/player-groups/${g.id}/members?playerIds=${Number(id)}`);
  } else {
    await api.post(`/player-groups/${g.id}/members`, { playerIds: [Number(id)] });
  }
  const groups = await api.get<PlayerGroup[]>(`/player-groups/by-player/${id}`);
  setPlayerGroupIds(groups.map((gr) => gr.id));
}}
```

**Стало:**
```tsx
onChange={() => {
  // Оптимистично: сразу обновляем UI, запрос — фоном
  setPlayerGroupIds((prev) =>
    isIn ? prev.filter((gid) => gid !== g.id) : [...prev, g.id]
  );
  if (isIn) {
    api.del(`/player-groups/${g.id}/members?playerIds=${Number(id)}`).catch(() => {
      // Откат при ошибке
      setPlayerGroupIds((prev) => isIn ? [...prev, g.id] : prev.filter((gid) => gid !== g.id));
    });
  } else {
    api.post(`/player-groups/${g.id}/members`, { playerIds: [Number(id)] }).catch(() => {
      setPlayerGroupIds((prev) => isIn ? [...prev, g.id] : prev.filter((gid) => gid !== g.id));
    });
  }
}}
```

**Зачем:** Сейчас при клике на чекбокс группы есть пауза: клик → запрос → ответ → перерисовка. С оптимистичным обновлением чекбокс переключается мгновенно, как будто это локальное состояние. Если запрос упал — откат.

#### Шаг 6. `AbortController` в useEffect (2.10)

**Где:** `PlayerCabinetPage.tsx` — useEffect для загрузки данных.

**Было:**
```tsx
useEffect(() => {
  api.get<PlayerMe>("/player/me").then((data) => {
    setMe(data);
    ...
  }).catch((err) => {
    setCharactersError(err instanceof Error ? err.message : String(err));
  });
}, []);
```

**Стало:**
```tsx
useEffect(() => {
  const ac = new AbortController();
  api.get<PlayerMe>("/player/me", { signal: ac.signal }).then((data) => {
    setMe(data);
    ...
  }).catch((err) => {
    if (err instanceof DOMException && err.name === "AbortError") return;
    setCharactersError(err instanceof Error ? err.message : String(err));
  });
  return () => ac.abort();
}, []);
```

**Зачем:** Если пользователь уходит со страницы, пока идёт запрос, console.showит ошибку «setState on unmounted component». AbortController отменяет запрос при размонтировании.
