## 3. Breakdown размера

Метод: для каждого поля каждой записи — длина UTF-8 от `json.dumps(value)`,
сумма по всем записям. Имена ключей, запятые и скобки JSON **не входят**
(поэтому сумма значений 123.42 MiB против 123.96 MiB файла — overhead ~0.5%).

```text
Полный catalog.json:           123.96 MiB

avatar_large_url:              104.17 MiB   84.03%
avatar_preview_url:             14.62 MiB   11.79%
description:                     3.42 MiB    2.76%
data:                            0.91 MiB    0.73%
name (+original/kind/id/...):    0.26 MiB    0.21%  (все структурные поля разом)
sections/system:                 ~0.00 MiB    ~0%
```

Детали: `description` — среднее 993 байта, медиана 709, max 14.3 КБ, пустых 162.
`data` — среднее 263 байта, медиана 139, max 25.3 КБ. Средний entry — 36 КБ
(искажено картинками), **медианный — 1310 байт**, max — 1.38 МБ (Ааракокра-застрельщик).
**Вывод из цифр:** структурные поля и метаданные вместе — четверть мегабайта;
оптимизировать нечего, кроме картинок.

## 7. Где используются картинки (карта по коду)

Client-компоненты читают только `avatar_image_url` (серверное поле); 1shot подставляет
его в `presentEntry` (`transport.ts:16`, `standalone-transport.ts:8`):
списки/batch → **preview**, одиночная запись → **large**.

```text
avatar_preview_url
→ CardTile/CardPicture сетки (DndCards.tsx:45-82) — визард: классы/подклассы/виды/
  предыстории/черты; option.card из dndCompendium.ts:97,104,158 (списки = preview)
→ DndCharacterForm:10394 (option-карты), :5009 (entry-карта, источник — batch = preview)
→ лист/визард: плитки заклинаний/предметов/особенностей (через те же option-карты)
→ нужен preview (маленький), full-size не нужен

avatar_large_url
→ GET /systems/entries/:id — детальные виды + аварийный перезапрос CardPicture
  при протухшей картинке (DndCards.tsx:69-71)
→ EntryBlurb/деталь записи (одиночный fetch = full=true)
→ нужен full-size только там, где запись открыта крупно; в списках не участвует
```

**Факт:** оба поля player-facing достижимы в 1shot. Large — только точечно
(деталь/ретрай), preview — массово (все сетки). Ни один компонент не читает
`avatar_preview_url`/`avatar_large_url` напрямую — только через `avatar_image_url`.

## 8. Portable HTML и media

Факты из `export-audit.mjs` + `portable.mjs` + `standalone.tsx`:
- В срез попадают только связанные записи (замер: 36 из 3605 для стаба 5 уровня);
  **все аватары среза удаляются** (`portable.mjs:28-34`: preview, large, image_url, data).
- Портрет — только `character.portrait` (data-URL); внешние картинки — жёсткий отказ
  экспорта (`portablePayload` throw + `audit.externalAssets`).
- **Следствие:** `large` (и вообще каталоговые картинки) для portable **не нужны** —
  удаление `avatar_large_url` из локального каталога portable-экспорт не ломает
  (доказано кодом: экспорт их стирает до сериализации).

## 9. Backup и browser storage

Замер настоящим кодом (`cat_part3.mjs`): реальный каталог + синтетический, но валидный
персонаж 5 уровня (класс/подкласс/вид/предыстория/10 заклинаний/12 особенностей/10 предметов,
`auditExport`: 36 связанных записей, 0 проблем). Оговорка: существующего живого персонажа
в IDB браузера не было — стаб собран из реальных entry id; размер персонажа 6.7 КБ —
порядок, типичный для документа (пустой лист — сотни байт, развитый — единицы–десятки КБ).

```text
backup A: 123.97 MiB (персонаж 6.7 КБ = 0.01%, каталог 99.99%)
backup B:  19.72 MiB (каталог 99.97%)
backup C:   5.01 MiB (каталог 99.87%)
```

Портрет в стабе `null`; реальный портрет добавляется 1:1 (типично сотни КБ — единицы МБ).
Для сравнения — portable HTML того же персонажа: payload 0.13 MiB,
**готовый HTML 4.22 MiB** (шаблон 4.10 MiB, срез 0.13), gzip 2.36 MiB, brotli 1.32 MiB.
Бэкап A тяжелее автономного HTML в **~29 раз** — почти целиком за счёт large-карт.

IndexedDB (оценка, не прямое измерение — браузерных инструментов в среде нет):
хранится structured clone ≈ JSON-объём, в Chromium строки идут как UTF-16 —
закладывать **1–2× от raw JSON** на копию. При отсутствии GC (факт из In_Audit) версии
умножаются линейно: 1/3/5 копий каталога A ≈ 124–248 / 370–740 / 620–1240 МБ;
B ≈ 20–40 / 60–120 / 100–200 МБ; C ≈ 5–10 / 15–30 / 25–50 МБ.
Квоты браузеров (обычно сотни МБ–ГБ на origin) вариант A при нескольких версиях
начинает заметно есть; B/C — безопасны с запасом. Точное измерение — через
`navigator.storage.estimate()` в живом браузере (не выполнялось).

## 10. Выводы по вопросам A–E (только из измерений)

**A. Хватит ли убрать только large?** Цифры: raw 19.9 MiB, провод 12.7 (gzip) /
11.2 (brotli) MiB, IDB-копия 20–40 МБ. Это уровень «тяжёлая, но обычная страница»
(сопоставимо с шаблоном portable). Достаточно ли — продуктовое решение; технически
авто-загрузка становится из «невозможной» (90 MiB) «тяжёлой, но рабочей».

**B. Только preview:** пользователь скачивает 11–13 MiB (brotli/gzip); raw 19.9 MiB.

**C. Без картинок:** rules/content-каталог — raw 5.1 MiB, провод **0.94 / 0.55 MiB**.
Чистый контент ничтожен относительно картинок (4% raw-файла).

**D. Главный источник веса:** originals (`large`) — 84%; затем previews — 12%;
descriptions — 2.8%; data — 0.7%; всё остальное — 0.2%. Ответ: **originals**,
с большим отрывом. Внутри originals — карты подклассов (~800 КБ × десятки).

**E. Нужно ли разделять rules и media?** Данные: без originals единый JSON — 19.9 MiB
raw / ~11 MiB провод; rules-ядро отдельно — 5.1 / 0.55. Разделение имеет смысл, только
если ~11 MiB всё ещё много (тогда C+подгрузка previews лениво даёт 0.55 MiB старта).
Если ~11 MiB приемлемы — один JSON-B уже решает 86% проблемы одним удалением поля,
без новых форматов, manifest и media-паков. Решать — вам; цифры выше.
